# Navigation & Input (the UX grammar)

## Context and Design Philosophy

This leaf owns how a human drives clowder from a keyboard: the key model, section navigation, the action model (select / act / repeat / bulk / confirm), the inspector, the glanceable chrome, discoverability, and how events and the offline report surface. It exists as its own leaf because the UX is the part the player *lives in* — it constrains the theme, the render layout, and the runtime, so it is designed first and in full.

**The one-sentence grammar:** sections are digits, items are a cursor, Enter does the thing, Space tells the truth. Every player-facing verb in `clowder_core::Command` is reachable as a *row in a list* (the discoverable backbone) and the frequent ones also carry a single-letter mnemonic (the speed layer). Nothing a player can only reach through a mnemonic or the palette; those are pure accelerators. One verb is the exception: appointing a kitten Elder is reached by the key `n` from that kitten's own row — a row the cursor reaches — so that each kitten stays one row (The Action Model: a kitten's one row).

The design is bounded by the HLD's tmux-first key constraint: the only usable keys are **plain printable characters, Tab/BackTab, Enter, Esc, Space, Backspace, and the arrow keys** — no Ctrl chords (Ctrl-C is emergency-quit only), no Alt/Meta, no function keys. **Uppercase is treated as the modifier tier** (Shift emits plain printable characters, which tmux never intercepts), and the tier is kept to one key, `X` — the bulk act a chord would otherwise have carried (see the Key Map).

## The Four Layers

A cold player learns the scheme in order; layer 1 alone plays the whole game.

1. **Backbone (minute one):** `↑`/`↓` move a list cursor, `Enter` performs the focused row's primary action, `Tab` moves to the next section.
2. **Truth (minute two):** `Space` opens the inspector on the focused row — exact costs, rates, effects, and *why* a thing is locked.
3. **Speed (hour one):** digits `1`–`0` jump to sections; per-screen letter mnemonics mirror the hottest rows; `x` acts with a typed count, `X` acts to the max affordable.
4. **Fast travel (week one):** `/` opens a find-anything palette over all *revealed* content.

Why a cursor is the backbone: 53 structures + 59 ideas + 35 refinements cannot be addressed by 26 letters or 10 digits, and progressive reveal inserts rows over time — a per-item hotkey scheme would relabel every key below an insertion (the renumbering hazard). A cursor scales to arbitrarily long, growing lists and is the most discoverable idiom in terminal software.

## The Key Map

### Global (a screen focused, no prompt/overlay open)

| Key | Action |
|---|---|
| `1`–`9`, `0` | Jump to that section (static map — see Navigation). An unrevealed digit is a soft no-op with a footer whisper. |
| `Tab` / `BackTab` | Next / previous *revealed* section |
| `l` / `h` | Synonyms for next / previous section (full hjkl) |
| `→` / `←` | Synonyms for next / previous section |
| `↓` / `↑` | Move the list cursor |
| `j` / `k` | Synonyms for cursor down / up (full hjkl) |
| `[` / `]` | Jump to previous / next group header within the list |
| `Enter` | Focused row's primary action ×1; commits an armed row |
| `Space` (`i` synonym) | Toggle the inspector on the focused row |
| `x` | Open the count prompt for the focused row, on a row that takes a count (digits captured); `Enter` applies ×N |
| `X` | Focused row's action × max affordable, on a row that takes a count |
| `+` / `=` | Increment on count rows (assign a worker/tinkerer) — Enter synonym there |
| `-` / `Backspace` | Decrement on count rows (unassign) |
| `/` | Find-anything palette over revealed content; `Enter` jumps to the top result |
| `e` | Journal overlay: full event scrollback + pinned offline/nap reports |
| `o` | Observe the sky (`ObserveSky`) — meaningful while the `!sky` chip shows; else a footer whisper |
| `<` / `>` | Game speed down / up one notch on the ladder 0.25 → 0.5 → 1 → 2 → 4 → 8 (`SetSpeed`); current speed is always in the header |
| `?` | Help overlay: full key map + glyph legend |
| `q` | Quit immediately (the shell saves first); no confirmation — quitting is always safe |
| `Esc` | Close the topmost transient (prompt, palette, overlay, armed row, narrow-mode inspector swap, banner) — one per press. On a bare screen: **no-op** |
| `Ctrl-C` | Emergency quit; saves first |

### Prompt contexts (count prompt, palette field)

| Key | Action |
|---|---|
| any printable char / `Space` (palette) | Typed into the query — letters, digits, symbols, and `Space` alike |
| digits `0`–`9` (count prompt) | Typed into the count |
| any other printable char / `Space` (count prompt) | Nothing — no text and no footer, as for any key with no binding in its context; a count is digits only, so there is nothing else for these keys to mean |
| `Backspace` | Delete the last character (nothing on an empty field) — never the global decrement |
| `↑` `↓` `←` `→`, `Tab` / `BackTab` | Nothing — the field holds the keyboard, so the cursor and section beneath it stay put |
| `Enter` | The field's own — the count prompt applies ×N (or cancels on an empty or zero count); the palette jumps to its top result, or does nothing with no query or no match. The press is spent on the field: the row beneath is reached only through the field's own act (the count prompt's ×N), never as a plain `Enter` on it; an armed row beneath is never committed by it; and holding it on never acts on the row the field returns to |
| `Esc` | Cancel; nothing happened |
| `Ctrl-C` | Emergency quit, as everywhere |

In both fields every global single-key binding is suspended, which is how digits stop being section-jumps while typing. The palette is a field under this table, not a full-screen overlay: it captures the speed keys and `q` as query text, where the Journal and help keep them live. A field never expires — it waits, the sim ticking beneath it, until `Esc` closes it or an `Enter` the field acts on does: the count prompt's `Enter` always closes it, the palette's only when there is a result to jump to. Walking away mid-type blocks nothing and loses nothing. While a field is open the hint bar shows that field's keys, even over an armed row beneath it, because the field is what `Enter` will reach.

### While waking (a load's catch-up replaying; The Waking Screen)

| Key | Action |
|---|---|
| `q` | Save and quit, as everywhere; the meadow finishes waking at the next load |
| `Ctrl-C` | Emergency quit, as everywhere; saves first |
| any other key | Nothing — discarded, not held for the game |

### Per-screen mnemonics (shown in the hint bar; each mirrors a listed row, save the one row-bound key)

| Section | Keys |
|---|---|
| Meadow | `g` gather · `f` forage · `r` rummage (appears when its row does) |
| Clowder | `p` promote (kitten) · `n` appoint Elder (kitten) — `n` the row-bound key below, not a mnemonic; job rows use `+`/`-` |
| Friends | `p` send a pen-pal (colony) |
| others | none — rows + Enter suffice; letters are spent only where frequency demands |

The help overlay lists every letter in the table's words, the Clowder screen's `n` among them. A letter whose row is a later row of its item is worded by that row's label (Action Model: an item's rows), in the table, the help overlay, and the hint bar alike (Mnemonics in the hint bar), so its act reads the same wherever its letter is named. The table and the overlay follow a focused-item letter's act with the item it acts on, in parentheses, since they are read away from the row; the hint bar, drawn while the cursor is on that item, leaves the parenthesis out.

**What a mnemonic stands for.** A mnemonic (a screen mnemonic: each belongs to one screen) is a lowercase letter that stands for one row listed on its screen — a row the cursor and `Enter` already reach, so the letter gates nothing (TUI-NAV-039). It comes in two kinds. A *fixed* mnemonic stands for one fixed row of its screen: the Meadow's gather, forage, and rummage rows. A *focused-item* mnemonic stands for a row of the item the cursor is on — the focused kitten's row, the focused colony's pen-pal row — an item being the thing a row is about, as the palette counts items (Resolved Edge Cases). On any screen a letter stands for at most one row at a time. A heavy row never carries a mnemonic: an arming belongs to the row under the cursor, whose distinct second `Enter` commits it (TUI-NAV-051), and a letter that armed a row elsewhere would leave that committing press aimed at a different row.

**When a mnemonic is live.** A fixed mnemonic is live while its row is listed on the focused screen. A focused-item mnemonic is live while the cursor is on a row of an item whose rows include the one it stands for — a kitten's one row for the Clowder `p`, either of a colony's two rows for the Friends `p`. The Clowder `p` stands for the very row it is live on, so the hint bar never names it (below); it answers there as that row's `Enter` does, and the help overlay lists it. A mnemonic is bound only while it is live, and only where the global table is: an open field takes its letter as text, and a full-screen overlay suspends it with the other action keys. A letter that is not live is an unbound key, ignored with no footer note (TUI-NAV-042): a note would whisper about a row the player has not reached, or chide a letter pressed off the item it acts on. Every letter the hint bar names is live, so a letter the player is shown always answers; the bar need not name every live letter, and one it leaves unnamed (below) still acts.

**What a mnemonic does.** A live mnemonic performs its row's primary action once, exactly as `Enter` on that row would: the core arbitrates, a refusal is the plain-language footer (TUI-NAV-014), and an owned item's row answers as TUI-NAV-041 has it. It moves neither the cursor nor the focused section, so it is an act, not navigation: the report banner and the layout stand as they were. Held, it acts no more than ten times a second, the pace a held `Enter` keeps, whatever the terminal's key-repeat rate.

**Mnemonics in the hint bar.** Wherever the hint bar shows the focused row's keys — no field, full-screen overlay, or armed row holding it — it names every live mnemonic except one whose row is the focused row, where `Enter` already names that act. Letters rank by how near they sit to the cursor. A focused-item mnemonic is the other act on the item under the cursor — the item `Enter` acts on — so it is named directly after the key that names `Enter`, among that item's own keys, and outlasts the inspector and section keys when width runs short (TUI-NAV-045). A fixed mnemonic acts on a row the cursor is not on and serves a player who already knows the screen, so the fixed mnemonics are named after every other context key, in their rows' list order, just before the help key — the first keys dropped when width runs short. A focused-item letter whose row is a later row of its item is named by that row's label — `p send a pen-pal` — so the act reads the same beside the letter as on its row. A live letter the bar leaves unnamed, its own row's or one dropped for width, still acts, and the help overlay lists every letter.

**The row-bound key.** One letter is bound to a row without standing for one: `n` on a kitten's row. A kitten is one row, whose `Enter` promotes it (The Action Model: a kitten's one row), and appointing that kitten Elder is the row's second act, reached by `n` alone. It is the one sectioned command no row takes as its `Enter`, and `n` is the one key of its kind; every other letter a screen spends is a mnemonic under the rules above, the Clowder `p` among them, standing for the kitten's row itself.

- *When it is live.* `n` is live while the cursor is on a kitten's row and the core reports the gate of `AppointElder` for that row's kitten open (SIM-ENG-045), and only where the global table is: an open field takes it as text, as the palette does, or ignores it, as the count prompt does (TUI-NAV-037), and a full-screen overlay suspends it with the other action keys (TUI-NAV-052). The narrow-mode swap is a layout, not a field, so `n` acts there as in the list view. Anywhere else — on a job row, a fixed row, another screen, a focused section that lists nothing, or with the gate closed — it is an unbound key, ignored with no footer note (TUI-NAV-042), as a mnemonic that is not live is. Which kittens the core would accept is the core's to say: the key is live on every kitten's row while the gate is open, the Elder's own row included, and the core arbitrates the press. On the Elder's own row the row and the hint bar leave the key unnamed (below), there being nothing left for it to offer, but the shell holds no rule that withholds it: a press there is issued and answered as on any kitten's row.
- *What it does.* A live `n` issues `AppointElder` for the kitten the row is about, once, as `Enter` would issue a command on a row: the core arbitrates, and a refusal is the plain-language footer (TUI-NAV-014). It moves neither the cursor nor the focused section, so it is an act, not navigation, and leaves the report banner and the layout as they were. Held, it acts no more than ten times a second, the pace a held `Enter` and a held mnemonic keep, whatever the terminal's key-repeat rate. The kitten's row is never heavy, so no arming stands where `n` is live.
- *How an appointment is answered.* Where the core accepts the command, the press is answered where the player is looking: one footer note, on the line a refusal's note takes and lasting as one does, saying in plain words that the kitten is the Elder. It names the kitten the core holds as the Elder once the command is accepted, by that kitten's whole name as the core holds it — never a form a row has shortened to fit its column — so it states the result as the core has it and reads true whether the press appointed a new Elder or the kitten already holding the role; each further press the core accepts, a held `n`'s included, leaves the same note anew. A press the core refuses leaves the refusal's note and no other (TUI-NAV-014). An appointment is the one accepted act the footer confirms. Every other act shows under the cursor as a count, a marker, or a cost that changes on the row it was taken from; an appointment shows at most as a mark arriving after the name, in the name's column (The Action Model: who the Elder is) — not at all on a row whose name leaves the mark no room, or while the narrow-mode swap has the list off screen — and a press on the Elder's own row changes nothing drawn. The ticker's line for the event (Event Log) is dim, away from the cursor, and one line among whatever else the meadow is doing, so it stands beside the note and never in its place. The Journal keeps the event's entry, and keeps it for good: the core classes an appointment as a milestone (Deferred).
- *Where it is named.* The key is named wherever it has something to offer, so the act the cursor cannot reach is never unseen where it can be taken. On the row: while the core reports the gate of `AppointElder` for a kitten open and that kitten is not the Elder, that kitten's row carries the hint `(n: Elder)` after the kitten's name, in the name's column, drawn in the theme's dim role and made of single-width characters only, so it reads as a quiet aside to the name and never as a marker, a count, or a cost. It never stands in the count or cost field's place, which on a kitten's row carries the word for what the kitten is doing (The Action Model: what a kitten's row says it is doing). The hint is drawn whole or not at all, since a cut hint names no key, and it never costs the name a character: the name is the row's identity, what the palette finds and the inspector names, while the hint repeats what the hint bar and the help overlay already say. So where the name's column cannot hold the whole name and the whole hint after it, the row carries no hint, and the name is drawn as any name is (TUI-RENDER-014). Where in the name's column the hint begins after the name is the render leaf's to state (Deferred). It is drawn on every such kitten's row, the cursor's and the rest alike, so a player reading down the roster learns the key before reaching the row it acts from; a row whose kitten's gate the core reports closed carries none, since the key it names is not live there, and the Elder's own row carries none, since the hint would offer what is already true — that row carries the Elder's mark in the hint's place, wherever its name leaves the mark room (The Action Model: who the Elder is). In the hint bar: wherever the bar shows the focused row's keys, while `n` is live and the focused row's kitten is not the Elder it is named `n appoint Elder`, directly after the key that names `Enter`, placed and ranked for width as a focused-item mnemonic is (TUI-NAV-045, TUI-NAV-082); while the cursor is on the Elder's own row the bar leaves it unnamed, a live letter the bar need not name (When a mnemonic is live). In the help overlay: among the Clowder screen's keys, as `n appoint Elder (kitten)`, in the table's words.

**Reserved keys that may never become a mnemonic of either kind:** every key the global table binds — `h j k l i x e o q`, uppercase `X`, the digits, `[ ] + = - / < > ?`, and `Space Enter Esc Tab BackTab Backspace` and the arrows. (Full hjkl was the player's choice; `h`/`l` cost two letters, but no screen wants them — mnemonics live on `g f r p`, and the row-bound key on `n`.) The row-bound key is held to the same reserve: no key the global table binds may become one.

**The uppercase tier has one member: `X`.** Mnemonics are lowercase, and no other uppercase letter is bound — an uppercase mnemonic is an unbound key, ignored silently like any other. Caps Lock already turns `x` into `X`; it must not also turn every mnemonic press into a bulk spend the player never asked for. The one key that acts in bulk is the one the hint bar names as bulk.

## Navigation & the Section Graph

Sections map to digits **statically, assigned at design time, never renumbered.** A section that unlocks late slots into its reserved digit; a key the player already knows never changes meaning.

| Digit | Section | Commands it hosts |
|---|---|---|
| `1` | **Meadow** (home) | GatherCatnip, Forage, Rummage, Build; a "stores" group lists every revealed resource as an inspectable row; energy & mess readouts |
| `2` | **Clowder** | AssignJob/UnassignJob, Promote, AppointElder (by `n` from a kitten's row), HostJamboree, Pounce(n) |
| `3` | **Ideas** | ResearchIdea, BuyRefinement, AdoptRule (three groups) |
| `4` | **Crafts** | Craft, AssignTinkerer/UnassignTinkerer |
| `5` | **Sunbeams** | Bask, Reverie, BuyRite, Enlighten |
| `6` | **Wonders** | HoldParade, BuyArch, RefineStarshard, RefineEcho, CondenseJar, MakePromise |
| `7` | **Friends** | Trade(colony, n), SendPenPal, ScoutPicnic |
| `8` | **Sky** | LaunchExpedition, SummonStarWhale, FeedWhale; whale exchange routed here while a whale visits |
| `9` | **Dreams** | DeepNap(years), BuyDreamLoom |
| `0` | **Legacy** | GreatMeadowMove, PassItDown, BuyTradition, DeclareAdventure, Family Album |

Global commands with no section: SetSpeed (`<`/`>`) and ObserveSky (`o`). Journal (`e`) and Help (`?`) are overlays, not sections. All ~40 command variants are covered.

**Growth under progressive reveal.** A section's tab follows its list: it is in the tab bar while the section lists something to point at, and absent before that (tab names are content, so no teasing tabs). Because digits are pre-assigned, a tab that arrives late appears in its fixed slot and no learned key shifts. A tab that arrives during play wears a `★` badge (glyph, not color) until its section is visited. The tabs in the bar are the revealed sections: `Tab`/`h`/`l`/arrows cycle only those, and a digit jumps only to one of them.

- *Which sections have a tab.* A section has its tab while its list holds at least one selectable row — a content row, a fixed action row, a kitten's, colony's, site's, or declare-list row, or a display-only stores row alike; a group header, a signpost the cursor never lands on, never counts. The section in focus also keeps its tab for as long as it holds focus, whether or not it lists a row (a focused section that empties, Resolved Edge Cases). Both are re-derived from current state and focus on every frame, so the same game state and focus show the same tabs whether the state was reached live or loaded; the one tab focus adds is the focused section's own, and a load always opens on the Meadow, which has its tab by its rows alone. The shell holds no reveal of its own: which rows are listed is the core's answer (TUI-NAV-053), and a tab only follows them. Rows leave a list where the core stops listing them — content a Move resets, a command's gate closing, a site's row once that site is reached — and a section whose last row has left loses its tab once it is out of focus, until a row returns. No action goes with it: a section that lists nothing holds nothing to act on, and every row is reachable through its tab whenever it is listed. The Meadow's tab never leaves, since its gather row's gate is always open.
- *Where a tab sits.* The tab bar lists the sections that have tabs in digit order, `1` through `9` and then `0`, each in its own slot, so a tab that appears late lands between its neighbours by digit and never pushes a learned tab to another key.
- *The badge.* A tab wears `★` from the moment it appears in the tab bar until its section is next visited. A visit is any entry into the section: its digit, a section cycle landing there, the palette's jump (TUI-NAV-065), or the opening focus (Resolved Edge Cases). A tab appears when it enters a tab bar that was not showing it — after a reveal, a gate opening, a nap, or a Move — so a tab that leaves and later returns is badged again: its return is a change to the tab bar the player has not yet looked at. That holds even where the rows it returns with are ones the player knows — a command's gate that closed for a while and reopened (SIM-ENG-045) brings its rows back unchanged — and the badge then marks a known tab until one visit clears it, a cost accepted in the Decisions & Alternatives. The tabs present when the game opens have not appeared: the opening takes what it finds as known (Resolved Edge Cases).
- *The Journal.* The shell adds nothing to the Journal for a tab's arrival: the Journal is the core's retained journal and holds no entry of the shell's making (TUI-NAV-026). What it holds of whatever brought a tab's first row is whatever events the core retained for it, which may be none — a gate reopening emits no event. The badge is the one mark the shell gives a tab's arrival.
- *The focused tab.* The tab bar says which section is in focus. The focused tab's label — its digit and its name, in the full form and the compact strip alike (Resolved Edge Cases: tab bar overflow) — is drawn in reverse video, the terminal's own foreground and background swapped (theme leaf: Three Things the Palette Does Not Cover). Every other tab's label, and every blank column between tabs, is drawn plain. The reversal is a fill rather than a colour, so it reads with every colour stripped, and it is the one mark on the bar that says where the player is: in the full form every tab is named, and in the compact strip a badged tab is named as the focused one is, so a name alone never tells which tab holds focus. Exactly one tab is reversed on every frame that draws the tab bar: a section is in focus from the opening focus onward (Resolved Edge Cases), and the section in focus always keeps its tab, a focused section that empties included. The reversal follows focus alone — it moves on the frame that a digit, a section cycle, or the palette's jump moves focus — and while a field or a full-screen overlay is open it stays on the section beneath, the one the player returns to. It adds no column to a label, so the width at which the bar takes its full form or its compact strip is the same whichever tab is in focus. The focused tab never wears `★`: entering a section is a visit, and a tab in focus never leaves the bar, so it cannot appear there again while focused.
**Groups within a section.** A section's list is broken into groups, so the eye finds where one kind of thing ends and the next begins and `[`/`]` have somewhere to go. The rule is one group per kind: every row is about something — a structure, a job, a kitten, a resource, a colony — and the rows about one kind of thing stand together in one group, never split across the list or mixed with another kind. A section's own fixed actions — the rows that are about no content item, the section's verbs — are one kind between them. An item that carries several rows (a craft's two, a colony's two) puts all of them in its kind's group, adjacent as always (an item's rows, The Action Model). Within a group, fixed actions stand in the order the table below names them, and every other kind in the order the core lists it, kittens by roster position.

| Section | Its groups, in order (header words) | What each holds |
|---|---|---|
| Meadow | `things to do` · `structures` · `stores` | gather, forage, rummage · every revealed structure's build row · every revealed resource (TUI-NAV-049) |
| Clowder | `jobs` · `kittens` · `things to do` | every revealed job's count row · every kitten's one row · host a jamboree, pounce |
| Ideas | `ideas` · `refinements` · `rules` | research rows · refinement rows · rule rows |
| Crafts | one group, no header | every revealed craft's make and tinkerer rows |
| Sunbeams | `things to do` · `rites` | bask, reverie, enlighten · every revealed rite |
| Wonders | `things to do` · `arches` | hold a parade, refine starshard, refine echo, condense a jar, make a promise · every revealed arch |
| Friends | `colonies` · `things to do` | each listed colony's trade and pen-pal rows · scout a picnic |
| Sky | `sites` · `things to do` | every reachable site's launch row · summon a star whale, feed the whale |
| Dreams | `things to do` · `loom upgrades` | deep nap · every revealed loom upgrade |
| Legacy | `things to do` · `traditions` · `adventures` | the Move, pass it down · every revealed tradition · the declare list, its no-adventure row first |

- *Where groups stand.* A section's groups stand in the order the table gives, the same on every frame, so no group moves as another comes or goes. A section's fixed actions stand together in their one group even where the core lists them at different times, so a section reads as its verbs and its things, never as verbs scattered among things.
- *The group header.* Each group is headed by one group header, directly above the group's first row, naming the group's kind. It is a signpost line the cursor never lands on and that `[`/`]` move between (TUI-NAV-007): where the cursor is placed on a section's first row (TUI-NAV-032), that is its first row beneath any header. A section whose design gives it a single kind — Crafts — draws no header: a header there would only repeat the tab's name. A section whose design gives it several kinds heads each of its groups, the first included, so the list reads the same however many of its groups are listed now, and a group that arrives brings only its own header, at its own place: no header is ever inserted above rows of a group already shown, which would push the cursor's row down the pane.
- *An empty group draws no header.* A group's header stands only while the group lists at least one row — a Teased row counts, since it is listed — judged on the rows the section lists after every gate the core reports (TUI-NAV-053): a header is never left above nothing, and a section never lists a header alone. A group whose last row leaves takes its header with it; a group whose first row arrives brings its header back.
- *Header wording.* A header is a short lowercase noun phrase, plural, naming the kind of thing its rows are about — never what they cost or how many there are, so it carries no figure and changes with nothing but which groups are listed. Each kind is named by the plain plural the game's design uses for it — `structures`, `jobs`, `kittens`, `ideas`, `refinements`, `rules`, `rites`, `arches`, `colonies`, `sites`, `loom upgrades`, `traditions`, `adventures` — and resources by `stores`. A section's fixed actions are `things to do` in every section that has them, so the one kind that recurs reads the same wherever it does. A header names a kind, not an item: it is never a result in the palette (TUI-NAV-063) and never counts toward a section's tab (above).
- *How a header is drawn* — a `dim` rule across the list carrying its words — is the render leaf's (TUI-RENDER-023).

**Getting home & composition.** Home is `1` (Meadow), one keypress from anywhere. Spatial movement is uniform: `h`/`l`/`←`/`→`/`Tab` across sections, `j`/`k`/`↑`/`↓` within a list, `[`/`]` for long-list group skips, `/` for fast travel. Each screen remembers its focused item by **content identity, not index**, so returning restores your place even if reveals inserted rows.

## The Action Model

Every actionable thing is a row. Row anatomy (one aligned line):

```
▸ ● Sunny catnip patch    ×2    14 catnip
```

`▸` cursor · availability marker · flavor name — or, on a later row of an item that carries several, that row's label in the name's place (an item's rows, below); on a kitten's row, the name followed in its column by the row's `(n: Elder)` hint wherever the row carries one (Per-screen mnemonics: the row-bound key), or on the Elder's own row by the Elder's mark, wherever that row carries it (Who the Elder is) · owned count · next cost — save on a kitten's row, which states neither, where their place carries the word for what the kitten is doing (A kitten's one row: what a kitten's row says it is doing). Markers are **glyph-first, color-second** (CVD-safe): `●` affordable now, `◐` partially affordable, `○` revealed but not affordable, `✓` owned/done for one-shots. `Availability::Teased` rows render dim *with* their marker; Hidden content is absent. Every answer behind a marker is the core's; which answer stands behind which row is pinned under Resolved Edge Cases.

**An item's rows.** An item — the thing a row is about — usually carries one row. A few carry several, adjacent in their section, each doing a different thing with the item: a craft's make row and its tinkerer count row, a colony's trade row and its pen-pal row. Each stays a row of its own, because every sectioned command is reached as a row (TUI-NAV-039) and a letter only accelerates a row the cursor already reaches (TUI-NAV-046). The item's name heads its rows once: the first of its rows that is listed carries the name, and every later listed row carries, in the name's place, a label in plain words saying what that row does — `tinkerers` on a craft's count row, `send a pen-pal` on a colony's pen-pal row. So no two of one item's rows read alike, and a list never shows one item's name twice. A label reads as belonging to the row above it, subordinate to the name that heads the item; how the list sets it in its columns to read that way is the render leaf's (Deferred). It carries no glyph, so nothing beside the marker can read as a marker or the cursor. The name goes on the first of the item's rows that is listed, not on its first row outright, so the item stays headed by its name even should a gate ever list a later row without the first. A label is its row's own and never the item's name: the name is what the palette finds and shows, and what the inspector names on whichever of the item's rows the cursor stands, stating a later row's label beneath it (What the inspector states). Apart from its label, a later row is a row like any other — it wears its own marker, count, and cost, takes the cursor, and keeps its own identity.

**A kitten's one row.** A kitten is the one item with a second act that carries no row of its own. Each kitten in the roster is exactly one row in the Clowder section, headed by the kitten's name, and its `Enter` promotes that kitten, as the Clowder `p` does while the cursor is on it (Per-screen mnemonics). Appointing the kitten Elder is taken from that same row by the row-bound key `n` (Per-screen mnemonics: the row-bound key), which the row itself names in a trailing `(n: Elder)` and the hint bar names beside `Enter`, on every kitten's row but the Elder's own, which says instead, wherever its name leaves room, that its kitten is the Elder (Who the Elder is). So the roster reads as a list of kittens, each once, and the Elder appointment is the one sectioned command reached by a key rather than as a row's `Enter` — every kitten it can act on is still a row the cursor reaches, and the act is named on that row. A kitten's row carries no label, since no second row of the kitten stands beneath it to tell apart, and its inspector states none (What the inspector states). Crafts and colonies keep their later rows as above.

**What a kitten's row says it is doing.** A kitten's row states neither an owned count nor a next cost (What the inspector states), so the place those fields take on other rows is free on it, and there it names the kitten's state, so the roster reads as who is doing what. Every kitten's row names exactly one state, read from the kitten as the core holds it — where it is and which job it holds — with nothing worked out from either:

- *Away.* A kitten whose location is anywhere but home reads `visiting`, whether or not it holds a job. It keeps its job while away but is not working it: the job's count row does not count it (What the inspector states: owned count), nor does the idle chip (TUI-NAV-054). So its row says where it is rather than naming a job it is not doing, and the roster agrees with the counts above it.
- *At home, with a job.* The job's name, spelled as the job's definition names it — the spelling the job's count row in the jobs group draws — so a job reads one way on its own row and on every kitten holding it. A kitten bound to a recipe as a tinkerer reads its job as any other kitten does; which recipe it is bound to is the Crafts section's to say.
- *At home, with no job.* `idle`, the idle chip's own word (TUI-NAV-020), so the kittens the chip counts are exactly the ones whose rows read it.

The two words are plain lowercase words and no job is named by either, so neither is mistaken for a job. The word belongs to the row, not to the kitten's name: the palette finds a kitten by its name alone (TUI-NAV-063), and the inspector names it as before. Like everything a row draws, it is re-derived on every frame, so an assignment, an unassignment, a wandering, or a homecoming shows on the frame it lands. Being the Elder is not a job, and the word says nothing of it: who the Elder is is said by the Elder's mark, in the name's column (Who the Elder is). The `(n: Elder)` hint stays in the name's column exactly as the row-bound key has it, and that column keeps its width. Where in the row the word stands, and that it is drawn whole at every width, is the render leaf's (TUI-RENDER-024).

**Who the Elder is.** At most one kitten is the Elder, and the core holds which, or that none is (SIM-KIT-022). The shell reads that as it stands and holds no rule about it: it never works out who the Elder is or should be, and every surface below says what the core holds. The roster says it on the Elder's own row. After the kitten's name in the name's column, in the place the `(n: Elder)` hint takes on every other kitten's row, the Elder's row carries the Elder's mark: `◆ Elder` — the glyph, one blank column, and the word. So one column of the roster reads, row by row, either that `n` would make this kitten the Elder or that this kitten is the Elder, and the one row that differs is found by its shape.

- *Its form.* A glyph and a word, both of single-width characters, and no colour of its own: the mark is drawn in the row's own style, as the name is, reversed with the row under the cursor. The glyph is how the row is found at a glance down a column of parenthesised hints, and the word is how it is read without a legend; neither leans on colour (Colour is never the only channel). `◆` is the mark's alone — no marker, chip, badge, or event prefix wears it — and it stands after the name, never beside the marker's column, so it never reads as availability. The help overlay's glyph legend lists it as the mark of the Elder.
- *Which row.* While the core holds an Elder, the mark stands on the row of the kitten at the roster position the core holds, and on no other row; while it holds none — as in a new meadow, before any appointment — no row carries it. The mark follows the core's answer alone: it stands on the Elder's row whatever the kitten is doing, away from the meadow included, and whatever the gate of `AppointElder` reports, since the mark states a fact where the hint names a key. Like everything a row draws, it is re-derived on every frame, so on the frame an appointment lands the mark is on the new Elder's row only, and the row it left is drawn as any other kitten's row is, its hint back wherever that row carries one.
- *No hint beside it.* The Elder's row draws no `(n: Elder)` hint, and the hint bar does not name `n` while the cursor is on it (Per-screen mnemonics: the row-bound key): both would offer what is already true. The key itself stays live there, as on every kitten's row.
- *Where the name's column is short.* The mark never costs the kitten's name a character, as the hint never does. The name is drawn first, exactly as on any kitten's row — whole where its column holds it, shortened as any name is where it does not (TUI-RENDER-014) — and the mark takes only the room the name leaves, in whole steps, the row drawing the first that fits: the whole mark; the glyph alone; no mark. The steps are the same at every width the list takes: no width has a form of its own, and what a row carries follows only from how long its name is and how wide its column. The name is the row's identity — what the palette finds and the inspector names — and where two kittens' names differ only at their ends, as a name and its later namesake's do, those last characters are what tell the rows apart; a mark that took them would make the Elder's the one row in the roster harder to tell from its neighbours. So the word gives way first: the glyph alone still marks the row, and its word stands on every Elder's row with room for it, in the help overlay's legend, and in the inspector's line. No step draws the word in part. The glyph gives way last, and only on a row whose name fills its column or leaves less than the glyph's place after it. Such a row has no room for a hint either, so it reads as any long-named kitten's row does, and the roster is silent there about who the Elder is: the inspector's line for the row says it (What the inspector states: the Elder), as the footer's note did when the appointment was made. Room for the mark beyond what the name leaves — a place of its own on the row, or a wider name's column in the Clowder list — would close that gap, and is the render leaf's to give (Deferred). The mark never stands in the count or cost fields' place, so the word for what the kitten is doing is drawn as on any kitten's row (TUI-RENDER-024).
- *Not the name.* The mark belongs to the row, not to the kitten's name: the palette finds and shows the kitten by its name alone (TUI-NAV-063), and the inspector names the kitten by its name alone, the mark on a line of its own beneath.

The inspector says who the Elder is too (What the inspector states: the Elder), and a press of `n` the core accepts is answered in the footer (Per-screen mnemonics: the row-bound key).

**Repeat:** the cursor does not move on action, so holding `Enter` repeats via terminal key-repeat — but the shell **rate-limits repeated Enter to ~10/second** so behavior is uniform across machines (not hostage to the OS key-repeat rate). Repeat is for ordinary rows only: a heavy row's second Enter must be a *distinct* press, so a held key arms and stops there (TUI-NAV-051). Auto-repeat is a machine typing, not a player deciding, and the armed-row pattern exists precisely to make the deciding press deliberate — letting key-repeat satisfy it would defeat the whole mechanism at 10 commits per second. For the same reason neither `x` nor `X` can commit a heavy row: `X` refuses one outright, with a footer that the row takes a deliberate `Enter`, and `x` reaches only the one heavy row that takes a count (DeepNap), where its prompt's `Enter` arms and a distinct `Enter` still commits.

**×N:** `x` opens a count prompt on the focused row that captures digits and live-previews what the count will cost; `Enter` fires the command N times, or passes N where the command takes a count (`Pounce(n)`, `Trade(c, n)`, `DeepNap(n)`). Which rows take the prompt, and what its preview can show on each, are pinned under Resolved Edge Cases.

**×max:** `X` loops the command until the core rejects it (all-or-nothing spends make this safe), under a shell-side iteration cap, one unit per call. Where the core exposes a closed-form max, the hint bar names it ("X builds 7"). Which rows it runs on, what each call carries, when its calls are made, how a held `X` is paced, and how its stop is reported are pinned under Resolved Edge Cases.

**Count rows** (jobs, tinkerers): `+`/`Enter` assigns one, `-`/`Backspace` unassigns one, `x`/`X` scale.

**Confirm vs. instant — the armed-row pattern (no modals, ever).** Ordinary purchases are instant; the core's all-or-nothing spend plus the affordability markers make that safe, and a rejection renders as a ~4-second footer flash translating the `CommandError` to plain words ("Not enough catnip — need 12.4 more"), never a dialog. The **heavy, hard-to-undo** actions — GreatMeadowMove, PassItDown, AdoptRule (locks its sibling for the meadow), and DeepNap (after its count prompt) — use an inline two-step: the first `Enter` *arms* the row, expanding it in place to a consequence summary rendered from real state ("Move to a new meadow: N kittens remembered in the album, room for M in the basket, chest carries P% of stores — Enter to move, Esc to stay"); the second `Enter` commits. Arming auto-expires after ~8 seconds of wall-clock time, whatever the game speed, or on any navigation, silently. This is confirmation without blocking: the sim keeps ticking, the rest of the screen keeps rendering, and walking away simply disarms. What the summary states, and exactly what ends an arming, are pinned under Resolved Edge Cases. (`q` is deliberately *not* armed — quitting loses nothing, so it is instant.)

## The Inspector — truth one keypress away (often zero)

- **Wide layouts (≥ ~100 cols):** the inspector is a persistent right-hand pane, live-updating for the focused row. Truth is zero keypresses away.
- **Narrow (80×24):** `Space` swaps the inspector *in place of* the list (Esc or Space returns) — not a popup; the chrome and sim keep rendering.
- **The inspector call.** Whether the player has called for the inspector is one piece of view state, held at every width; the layout decides only how it is drawn — the swap where the narrow layout is on screen, nothing extra where the pane already shows the inspector. `Space` (or `i`) sets or clears the call only while the narrow layout is on screen, judged as `Esc` judges the swap: by the layout drawn when the key is pressed, the breakpoint's dead-band applied (TUI-NAV-030, TUI-NAV-047). Elsewhere there is no swap for the key to bring in or take out, so it leaves the call as it stood: a call flipped where nothing could show it would bring a swap in, or leave one out, at the next narrowing, a layout the player never saw chosen. So the view a player narrows into is always the one they last left at a narrow width, and the list view where they have left none this session. How the key answers where it leaves the call alone follows what the player can see:
  - *While the persistent pane is drawn,* the key stays bound, and the hint bar, whose keys follow the focused context rather than the layout (TUI-NAV-023), can name it there, so the key answers: it leaves one footer note that the inspector already stands beside the list. It is a bound key that cannot act now, and says so (TUI-NAV-042); a key the player may have been shown never meets silence.
  - *While the too-small card is drawn,* the key leaves no note. The card draws neither the hint bar nor the footer, so no key has been shown to the player and an answer would be drawn nowhere; a note left there would keep its own clock past the card and could surface at a narrow width, saying the inspector stands beside a list it is not beside.

**What the inspector states.** The inspector describes the row the cursor is on — the row the list highlights, re-derived every frame, so when a row leaves its list the inspector goes with the cursor to wherever it falls back (TUI-NAV-032). Its facts come from two places only: the content definitions, for what a thing *is* and does, and core queries, for everything current state decides — price, rate, cap, ownership, and why a thing cannot be taken now. Its figures take the inspector's exact, unabbreviated form (TUI-RENDER-012): it is where the exact form of whatever the row and the sidebar abbreviate is read.

- *Name.* The flavor name of the item the row is about, whole as the render leaf keeps it in the inspector (TUI-RENDER-014) — where a name the list cut with an ellipsis is read in full.
- *Which of its acts.* On a row the list draws with a label in the name's place — a later row of an item that carries several (Action Model: an item's rows) — that label, beneath the name and whole, as the name is kept whole. The name says which item the row is about and the label which of the item's acts the row takes; with the narrow-mode swap in, the list and its label are off screen, and the inspector is then the one place that says which act `Enter` will take. The inspector states it at every width, since what it states follows the focused row, never the layout. A row the list draws with the item's name carries no label, and its inspector states none: that row's act is the item's own, read from the name as on any single-row item.
- *The Elder.* On the row of the kitten the core holds as the Elder, one line beneath the name, the row's mark whole: `◆ Elder` (Action Model: who the Elder is). The list does not always say it: with the narrow-mode swap in, the list and its mark are off screen, and a row whose name leaves its column no room carries no mark at all. This line is then the one place that says the kitten under the cursor is the Elder, so the inspector states it at every width and whatever the row has room for, since what it states follows the focused row, never the layout. On every other kitten's row, and while the core holds no Elder, no such line is stated, its absence saying the rest. The line says who the Elder is and nothing of what being the Elder does: that is the core's rule, and a kitten's row has no definition to state it from (Mechanical statement).
- *Mechanical statement.* What the thing does, in its definition's own terms, per copy or per worker. For a kind whose definition carries a blurb — an idea, a refinement, a rule — the blurb is the statement: it is the definition's own sentence for what the item does, and the effect fields beside it are not restated, since a second statement of one effect reads as a second effect. For every other kind the statement is every field the definition carries apart from its name, its price and that price's escalation, its reveal threshold, and its gates, each stated wherever it departs from its nothing-special value — zero, empty, false, or none — and left out where it does not, a baseline field saying nothing. For a structure that is its productions, with each qualifier that shapes them (seasonal, scaled by the energy surplus, routed through the outdoor channel); the housing and storage it adds; its mood points and crowding relief; its per-resource, craft, outdoor, and global ratios; its bearing on luxury demand and on a jamboree; its converter's inputs and outputs; the mess it makes; the energy it makes and uses; and any extension it gives the long sun ("Produces 0.63 catnip/s per copy, seasonal"). For a job it is the yield per worker; for a craft, the resource it makes, as the content tables pair it with the recipe, and the work tier a tinkerer meets it at. A rite's, an arch's, a tradition's, and a dream loom's definitions carry nothing past name, price, and gate, so their rows have no statement. A field the definition carries per tick is stated per game second, as the sidebar states rates, converted by the core's ticks-per-second; a ratio is stated as the percentage it adds. The statement carries no price: the price on screen is the core's, and a table price beside it would disagree with it the first time an effect scaled it. It states no total for the copies owned and no yield after mood: what current state makes of a definition is the core's net rate to report, and a product worked out in the shell is a rule held outside the core. Where nothing is left to state — every stated field at its baseline, a blurb empty, or the row's action with no definition at all, as on a fixed action row or a kitten's row — there is no mechanical statement and no stand-in for one: a sentence that fits every item of a kind reads as a description while describing nothing.
- *Owned count.* For an item held in copies — a structure, a rite — the copies state holds. For a count row, the kittens it holds who are in the meadow: on a job's row, the kittens in the meadow holding that job, which is the core's worker count (SIM-KIT-010); on a craft's tinkerer row, the tinkerers in the meadow bound to that recipe. A kitten away from the meadow keeps its job and its binding but is not counted while away, since it is not working there — the same line the idle chip draws (TUI-NAV-054). An item held once states its ownership through its lock reason instead.
- *Next cost and the wait.* On a row that takes a content item — its build, research, purchase, or make, or the assign of a job's count row — the next cost is the core's price for one more (SIM-ENG-038, at a count of one), each component with need and have. Where that price names no component, no next cost is stated: the core prices a job's assignment at nothing and names no price outside the resource vocabulary, and the two read alike in its answer, so a stated "nothing" would be false for the second. A craft's tinkerer count row binds rather than makes, so it states no next cost. Only the core's lock reason marks components, since it is drawn from the gate `Enter` meets, tolerance included: where the reason is a shortfall, each component it names is short by the amount it names and each it leaves out is covered; where the core reports no reason, every component is covered; where another reason holds the item back, need and have stand unmarked. Beside each component the core reports short stands a wait: the shortfall divided by the core's net rate for that resource (SIM-ENG-030) and by the current speed, so the wait is in real time, stated in plain units of time and never rounded to sooner than the rate gives — advisory, as the rate is (SIM-ENG-035). Where the need exceeds the resource's cap as the core reports it, the component says the stores cannot hold that much yet, with no wait: the core clamps a capped stock to its cap (SIM-ECO-001), so a wait there would promise what no waiting delivers, and the comparison applies that stated rule rather than one the shell holds. Otherwise, where the rate is zero or less, the component says its stock is not growing just now, with no wait. Where both hold, the cap note stands alone: no growth closes that gap, and the stores are what would help. Where the core reports the item already the player's, there is no next to price, and no next cost is stated. A row whose action takes no content item has no content price: Pounce and Trade rows state the core's one-unit price instead (below), and every other such row states none.
- *Why it cannot be taken.* The core's lock reason for the item (SIM-ENG-031), in plain words, stated exactly where the core reports one and — as for the marker — only on the row that takes the item itself: a build, research, purchase, or make row, or a job's count row, whose `+` assigns. The core defines six reasons, and each has its own wording, so two reasons never read alike and the set of wordings is the core's whole set. A shortfall names each short component and the amount it is short by; a shortfall the core reports naming no component, for a price outside the resource vocabulary, says the price is not yet met and names no amount. Not-yet-reached says only that (SIM-ENG-037). A prerequisite reason says a prerequisite is unmet without naming it, the core naming none. Already-yours says the item is the player's already — how an item held once states its ownership. No-one-free says no kitten in the meadow is free to take it on; a job's count row meets it when every kitten in the meadow has work. No-room says there is no room for it yet; no listed row's kind meets it, and it is worded so that the wordings cover every reason the core defines. Neither a Teased availability nor a stock is a reason: where the core reports none, none is stated. A craft's tinkerer count row and every row with no content item state no reason, the core reporting none for them.
- *A stores row* describes its resource: its exact stock, the cap the core reports for it or that it has none, and the core's net rate for it per game second.

**A count-taking row's price is the core's price for one unit.** Pounce and Trade rows act on no content item, so the core's content-item cost queries do not price them; the core instead reports a count-taking command's price for one unit — one squad, or one caravan to the row's colony (Core API Dependencies). On those rows the inspector's next cost is that price, with have/need per component as for any cost, so a count-taking spend is priced before `x` is pressed; the count prompt then prices the count itself (Resolved Edge Cases). The inspector shows the price as the core reports it and reads none from the content tables, since a per-unit price assembled in the shell is the command's pricing rule held outside the core. The core reports no lock reason for these rows, and only a lock reason marks components, so need and have stand unmarked and no wait is stated beside them. DeepNap's price escalates with the years chosen, so the core reports no one-unit price for it; its row states the full cost once the count is known, on the armed row (TUI-NAV-036).

## Glanceability — the persistent chrome

Always on screen, at every size:

1. **Header (1 line):** clowder name/generation · season+day+year · kitten count · **mood as a word** · speed (`×1`) · right-aligned **attention chips**.
2. **Tab bar (1 line):** revealed tabs with digits; `★` on unvisited new tabs; the focused tab's label reversed.
3. **Resource sidebar (left column):** a curated glance — revealed resources with stock/cap, a 4-cell fill bar, and signed rate; a text `full` tag when capped. Full truth is in Meadow's "stores" rows.
4. **Log ticker** (1 line at 80×24, up to 4 lines wide): latest events, dimmed.
5. **Hint bar (1 line):** context keys.

**The two-second glance contract.** The header's attention-chip cluster is empty when nothing waits. Chips are curated *opportunities*, never obligations, each rendered as glyph and word, with a count between them where the opportunity is a quantity (CVD-safe, colour never the only channel):

- `◦N idle` — kittens with no job *who are in the meadow to be assigned* (free production you're leaving on the table); a kitten visiting the neighbour's yard is not counted, because the chip would then ask for an action the player cannot take
- `!sky` — an observable sky-event window is open (act with `o`; expires harmlessly)
- `★N new` — sections whose tabs have appeared on the tab bar since you last looked: N is the number of tabs wearing `★` (clears as each is visited)
- `~away` — an unread report of time passed in bulk waits, an absence's or a nap's (clears once every one is read)

Deliberately excluded: any "something is affordable now" chip — it would never be quiet, and quiet is the whole point. If the chip cluster is empty and no bar reads `full`, nothing needs you.

**The chips' form and order.** Every chip carries its glyph and its word, so neither the glyph alone nor the colour alone carries it. The two chips whose opportunity is a quantity carry a count between glyph and word, wherever the header's width keeps it (below): `◦N idle`, how many kittens wait for work, and `★N new`, how many badged tabs wait for a visit. `!sky` and `~away` carry none, the glyph standing directly before the word: the core holds at most one sky-event window at a time (SIM-ENG-025), and unread reports are walked one banner at a time with the Journal opening onto all of them (TUI-NAV-050), so a count of either would tell the player nothing more to do. The live chips stand right-aligned in the header in one fixed order — idle, sky, new, away — two blank columns apart, so a chip that comes and goes never trades places with another, the eye learns where each one lives, and the space inside a counting chip never reads as the gap between two chips.

**The header's width.** The header is one line: the facts TUI-NAV-019 names on the left, the live chips right-aligned, and at least one blank column between the last fact and the first chip, so a fact never runs into a chip and reads as part of it. Two things are never given up for width. No live chip is cut or dropped: a chip missing from the cluster is a live opportunity drawn as silence, which the glance contract reads as nothing needing the player — the one misreading the cluster exists to prevent. And no figure is cut: a number drawn in part reads as a wrong number, as it would on the report banner. Where the pane is too narrow for the full line, the header gives up width in fixed whole steps, drawing the first of these that fits:

1. *The full line.* The facts in their full wording, each apart from the next by ` · `: `Gen` and the generation; the season's name, `Day` and the day, `Year` and the year, as the core's calendar reports them; the kitten count and the word `kittens`; the mood word; `×` and the speed. Every live chip carries its count.
2. *Compact facts.* The same facts in the same order, each figure whole, in the compact wording: the labels before the generation, the day, and the year shorten to `G`, `D`, and `Y`, set directly before their figures; the season's name shortens to its first three letters; and the facts stand apart by a single space. The kitten count keeps its word, since a bare figure beside the year's would read as part of the date. The mood word and the speed are unchanged. The chips are as in step one.
3. *Chips without counts.* The facts compact as in step two, and the two counting chips drawn as glyph and word alone, as `!sky` and `~away` always are. Every live chip stays, each still saying that its opportunity waits, and the tab bar still shows each badged tab the `★` chip stands for.
4. *Facts shed.* The compact facts shed whole, one at a time, in the order the generation, the date, the kitten count, until the line fits; the chips are as in step three. The mood word and the speed are never shed: the word is mood's one channel (TUI-NAV-022), and the speed is always in the header (the Key Map).

Steps one to three keep every fact TUI-NAV-019 names, and they give way in the order that costs the glance least: the facts' labels before the chips' counts, and both before any fact. With the counts gone, the chip cluster's width is fixed, and the mood word and the speed fit beside all four chips at the floor width, so the steps always end in a line that fits. At the floor width with all four chips live, step three holds every fact while the generation, day, year, and kitten count together run to twenty-two digits — a nine-digit day count beside a two-digit generation and a four-digit kitten count, which at the fastest speed is years of unbroken play. Step four is reached only past that, where no line of the pane's width can hold every fact beside every live chip with each figure whole, so TUI-NAV-019's header cannot be kept whole whatever is chosen. There the header keeps the chips, whose absence would be misread as calm, over the date and the counts, whose absence reads only as absence.

**Colour is never the only channel.** Each of the four meanings TUI-NAV-022 names has a channel of glyph, word, or fill, drawn on the same line as any colour that marks it, so stripping every colour loses none of them. Affordability is the row's marker glyph (TUI-NAV-009), `●`, `◐`, `○`, and `✓` telling the states apart by shape alone. Mood is its word (TUI-NAV-019), and takes no colour at all. A capped store is the word `full` on the sidebar line that draws the store's fill bar. A store is capped where the core reports a cap for it above zero and its stock has reached that cap. The core trims every capped stock to its cap (SIM-ECO-003), so that comparison applies the core's own stated rule rather than a threshold the shell holds. A store the core reports uncapped is never capped, since it has no cap to reach (SIM-ECO-001). A store whose cap is zero is never capped either: it can hold nothing yet, so there is nothing in it to spend or move before it overflows, and `full` there would ask for the player's attention with nothing for them to do — the glance contract reads a `full` bar as something that needs them. Attention is each chip's glyph and word (above). What colour means across the whole palette, and that every such meaning is paired, is the theme leaf's (TUI-THEME-010). This leaf names the channel for the four meanings it owns.

**Glyph discipline:** UI symbols are single-width geometric/box-drawing characters only (`● ○ ◐ ▸ ▓ ░ ★ · ! ◦ ~ ◆`). No emoji anywhere — ambiguous-width glyphs break column math across terminals and tmux. Whimsy lives in the words and the color, not the symbols.

## Discoverability — the first 60 seconds

Cold open: only Meadow exists, its gather row focused ("Gather catnip") with the forage row beneath it — the Meadow entered from the very first frame, so its one tab wears no badge and `Enter` already has a row to act on (the opening focus, Resolved Edge Cases). The hint bar reads, in full:

```
 ↑↓ choose · Enter do · Space details · Tab next · f forage · ? all keys
```

The only possible actions teach the backbone, which leads the line; the one letter after it is the speed layer's first lesson, naming the Meadow action the cursor is not on (gather's own letter goes unnamed while `Enter` names that act). As surface grows, the hint bar adapts by context, most-relevant-first, always ending with `? keys`:

- buildable focused: `Enter build · x amount · X max · Space details`
- job row focused: `+ assign · - unassign · x amount · X max`
- a kitten's row focused: `Enter do · n appoint Elder · Space details`
- the Elder's own row focused: `Enter do · Space details`
- armed row: `Enter yes, truly · Esc not today`
- count prompt: `digits amount · Enter go · Esc never mind`
- palette: `type to find · Enter go · Esc never mind`

An open field's line wins over every other context, an armed row's included, since the field holds the keyboard.

The speed layer is taught lazily, at the moment of relevance: the hint bar names `x amount` exactly while the focused row is one `x` opens the count prompt on — a row tagged count-taking or repeat-N, or a count row, and not one the core reports as already the player's (Resolved Edge Cases) — so the key first appears the first time such a row is focused, and never beside a row where it would only earn a refusal. `X max` follows the same rule for the rows `X` runs on, so it is never named beside a heavy row, which `X` refuses (TUI-NAV-051); DeepNap's row names `x amount` alone. An open field's line or an armed row's takes the bar first, as above. `?` shows the complete key map and glyph legend. There is no manual; the hint bar and `?` are the manual.

## The Waking Screen

A load whose catch-up outlasts one frame's bound replays it behind the waking screen (runtime leaf: Waking Up). The screen stands in place of the game's frame: no header, tab bar, list, ticker, or hint bar, because none of them has anything true to say about a meadow still catching up — its numbers and tabs would race through states the player cannot act on. It holds three lines, centred in the pane:

```
              the clowder is stretching awake…

        ████████████████░░░░░░░░░░░░░░░░░░░░░░░░   41%

          q save & quit · the meadow finishes waking next time
```

- **The progress.** A bar forty cells wide and a whole-percent figure, both the share of the catch-up's owed ticks already replayed, read from the core's total and remaining counts (SAVE-018) — the shell works out nothing about the absence itself. Both round down, so neither reads full until waking ends, and waking ends by opening the game, so the screen never shows a full bar standing still. The bar fills with `█` and stands empty as `░`, so its share reads without colour.
- **What draws it.** The catch-up's counts and the terminal's size alone. Below 80 columns or 24 rows the too-small card draws instead, as it does in place of every frame (TUI-NAV-029, TUI-NAV-087), and the replay carries on beneath it.
- **Keys.** Quitting alone answers, by `q` or `Ctrl-C`, saving as it does everywhere (TUI-NAV-016): the runtime sets the catch-up down and saves what remains owed with the core's report so far, so nothing is lost and the next load wakes through the rest and tells the whole absence once. Every other key is discarded, not held: a key pressed at a screen that offered it nothing would otherwise act on a meadow the player has not yet seen — a cursor moved, a row bought, a speed changed over rows never drawn. An `Esc` fused with a following key under tmux's `escape-time` reads as an unbound chord and is ignored whole, as everywhere (TUI-NAV-001), so a fused `q` does not quit and the player presses again. A resize is not a key: the screen redraws at the new size.
- **How it ends.** When the replay finishes, the game opens (The opening focus, Resolved Edge Cases) and the first frame of play follows, the load's report banner first among what it shows, exactly as for a load that never needed the screen. A short absence that the first bound replays whole never shows the screen at all.

## Event Log & Offline Report

- **Ticker + Journal.** Typed `Event`s render into one dim ticker line (or a strip when wide). `e` opens the Journal overlay: full scrollback, `↑↓`/`j`/`k` scroll, `[`/`]` by day, Esc closes. Flavor events are quieter (dim, `·` prefix) than mechanical ones (`▪`); milestones get `★`. Nothing flashes, blocks, or expires unseen — the Journal keeps it all.
- **Offline report.** A report the core retains — the one a load's catch-up folds when it spans at least the core's minimum interval (SAVE-015), or the one every accepted nap returns (SIM-DREAM-008) — renders as (a) a one-line banner under the tab bar — reverse-video, not color-only: `~ while you were away (2d 4h): +12.4k catnip, 3 kittens arrived · e for the tale · Esc dismiss` — and (b) a pinned Journal entry with the full folded detail. The one line is *curated*, not a summary of the whole struct: elapsed span, the largest resource gains, and arrivals. Wanderings and other absences live in the pinned entry, where they are stated as what they are — a visit that ends back home, never a loss or a count going down. The banner is the first thing a returning player sees, so it leads with what grew. The banner dismisses on Esc or first navigation and demands nothing; the pinned entry means dismissing loses nothing. A `truncated` report renders as gentle flavor. `Event::Napped` reports reuse the same path — one mechanism for "time passed in bulk." Which reports get a banner, how the banners queue and retire, what the line holds at every width, and what the pinned entry tells are pinned under Resolved Edge Cases.

## Edge Cases

- **80×24 (floor):** header 1 + tabs 1 + body 20 (sidebar | list) + ticker 1 + hints 1. The body is whatever the chrome leaves — the `render` leaf states it as a formula so the rows always sum to the terminal's height. The inspector becomes Space-toggled; the log becomes a 1-line ticker; the offline banner replaces the group-header line when present. Everything stays reachable; degradation removes *simultaneity*, never capability. Below 80×24, render a calm "this pane is too cozy — 80×24 needed" card; the sim ticks regardless.
- **Very wide (~120+):** three columns — sidebar | list (capped ~60 cols for scannability) | inspector (rest). Extra width feeds the inspector and log.
- **Resize:** layout is a pure function of terminal size, recomputed per frame with breakpoints at 100 and 120 cols (the render leaf's TUI-RENDER-001 and TUI-RENDER-005 to TUI-RENDER-008). A resize changes how the view state is drawn and never the view state itself: cursor, per-screen memory, armed state, open fields and overlays, the banner, and the inspector call all survive it (an armed row that no longer fits re-renders compact, still armed). What it keeps is pinned under Resolved Edge Cases (What a resize keeps).
- **Keys inside a full-screen overlay:** the Journal and help overlays take the cursor, section, and action keys for their own navigation, suspending those global meanings while open. The speed keys, `q`, `Ctrl-C`, and `Esc` stay live — retiming the sim, leaving, and closing must work from anywhere, and all four are safe wherever they land. (The count prompt and the palette field differ: they capture *all* printable input, which is what stops a digit from jumping sections mid-type.)
- **Esc under tmux `escape-time`:** Esc *only* closes the topmost transient; on a bare screen it is a no-op. No Esc-prefixed sequences exist anywhere, so escape-time coalescing can never form a phantom binding, and a late Esc can at worst close a transient — never act, quit, or lose anything. Quit is `q` or Ctrl-C; both save. What each press closes, and what a fused `Esc` does, are pinned under Resolved Edge Cases (What `Esc` closes).

## Resolved Edge Cases

A self-probe of this leaf's own gaps; each is pinned so an implementer never guesses a load-bearing default.

- **Enter on a Teased/unaffordable row** always *attempts* the command; the core rejects (all-or-nothing), and the rejection renders as the plain-language footer (TUI-NAV-014). There is no separate "can't afford" pre-check in the shell — the core is the single arbiter, and the footer names what's short.
- **What a row's marker and presence rest on.** Every answer behind a row's marker, and behind whether a content row is listed at all, is a core query read as it stands. The shell draws no threshold of its own and works out no coverage from a price — not even by dividing a stock by the one-unit price the core reports for a Pounce or Trade row, which would be affordability judged outside the core. Rows are re-derived from current state on every frame, so a marker is always the core's answer for now.
  - *Presence.* A content row is listed while the core reports its item Teased or Available and the gate of the row's command open (SIM-ENG-045), and at no other time. Affordability is a marker, never a filter: emptying every stock changes what the rows wear, never which rows are listed or in what order, so a cursor that remembers an item by identity never loses it to a dip in stock. Which rows with no content item are listed is the section's own reveal rule (TUI-NAV-006), not this one.
  - *Kinds without a reveal ladder.* The core answers availability for every content kind, and a kind with no reveal ladder answers only present or absent (SIM-ENG-032). Such a row is shown present or not at all — never dimmed as a Teased row the core did not report — and wears the marker its lock reason gives, as every content row does.
  - *The marker.* A content row's marker is read from the core's lock reason for its item (SIM-ENG-031), which the core resolves by the same gate and precedence the command layer applies (SIM-ENG-036). Where that reason is that the item is already the player's, the row wears `✓`. Where the core reports no lock reason, the row wears `●`: `●` promises that `Enter` would take the item now, and the lock reason is the one answer drawn from the very gate `Enter` meets. Where the reason is a shortfall, the core's coverage of the item's price (SIM-ENG-039) picks between the other two — `◐` where it reports some coverage, `○` where it reports none. Any other reason — a prerequisite not yet met, a gate not yet reached, no kitten free to take a job — gives `○`, whatever the stock: a price in hand is not partway to an item something else holds back, and `◐` there would call it partly affordable when no stock could make it so. The coverage fraction never decides `●`, so the shell needs no view of how near to whole a fraction must come. A row whose item the core reports Teased is dimmed whatever glyph it wears, `◐` included, the dim read from the availability report itself (TUI-NAV-009); a row of a kind without a reveal ladder, never reported Teased, wears only its glyph's own colour. For a revealed item of a kind with a reveal ladder the core reports Available exactly where its lock reason names none (SIM-ENG-023, SIM-ENG-031), so the dim and the glyph never contradict each other: a Teased row never wears `●`, and a listed row of such a kind wearing any other glyph is Teased and dimmed. As a Teased row's stock grows its glyph only steps forward, `○` to `◐` to `●`, and changes otherwise only when its lock reason does. Ownership is read in the core's precedence too: where the core names another blocker ahead of ownership, the row wears `○` and a refused `Enter` names that blocker, exactly as the command layer would.
  - *Rows the core reports no lock reason for.* An item's lock reason and coverage speak for the row that takes the item itself — its build, research, purchase, or make, or a job's assign — never for a sibling row that does something else with it. A craft's tinkerer count row binds a tinkerer to the recipe rather than making it, and the core reports no lock reason for that bind, so it wears `●` while it is listed. A row with no content item — a fixed action row, a kitten's row, a colony's trade or pen-pal row, a site's row, or a declare-list row — has no lock reason or coverage the core reports, so it too wears `●` while listed: there to act on, `Enter` attempting it and the core arbitrating, as on a Teased or unaffordable row above. Its price, where it has one, is the inspector's and the footer's to state. A display-only row — a stores row — has nothing to act on or afford, so it wears no marker, its slot left blank so the names stay aligned.
- **A printable key with no binding in the current context** is ignored with no footer noise (only *meaningful-but-not-now* keys, like `o` outside a sky window, get a footer whisper).
- **An owned one-shot (`✓`) row** makes Enter, `x`, and `X` all no-ops with a footer ("already yours"). Ownership is what the core reports, not a shell-side judgement, and it is checked before anything else the key would do — so an owned heavy row (an adopted rule) never arms.
- **Count semantics.** The command an action row fires carries exactly one of three tags, the same wherever the command appears:
  - *count-taking* — Pounce, Trade, DeepNap: the count is a real argument (squads, caravans, years), passed through once; the core takes the count whole or rejects it whole, spending nothing on a count it will not take.
  - *repeat-N* — Build, Craft, and the buys (BuyRefinement, BuyRite, BuyArch, BuyDreamLoom, BuyTradition): each call takes one more copy of a content item, at a price the core totals from current state (SIM-ENG-038), and the shell calls the command N times. Calls run until one is rejected — partial success is intended (you build as many as you can afford; the core's per-call all-or-nothing keeps each build clean). How many copies an item takes is the core's to say, item by item and as state changes, never the tag's: an item the core restacks takes as many as the stock covers, and a one-shot takes one, after which the core reports it the player's and the owned rule above holds its row. A run that reaches that point stops at the core's refusal, as any run does.
  - *single* — every other command: gathering, researching an idea, the ceremonies and conversions, a kitten's, a colony's, or a site's own action, the declarations, and the heavy rows that take no count (the Move, PassItDown, AdoptRule). None of them takes a count as its argument or adds a copy of a content item, the two quantities `x` and `X` exist to scale — squads, caravans, years, copies, the things a player plans a spend around. Most act on no content item at all, and those that do (researching an idea, adopting a rule) take it once. Where one bears repeating, held Enter already repeats it, rate-limited, at a pace the player watches (TUI-NAV-010), and a heavy one must never repeat at all (TUI-NAV-051). So the bulk keys stay the keys for a quantity, and a single row is Enter's alone, one call per press.

  A count row is not an action row and carries no tag: it has an assign and an unassign rather than one command, and its scaling is fixed by being a count row — `x` and `X` repeat-call its assign, one kitten per call.

  `Enter` is ×1 on every row, so on a count-taking row it takes one unit: a Pounce or Trade row's `Enter` passes a count of one — one squad, one caravan — and the unarmed nap row's arms a nap of one year (the DeepNap sequence below), where an armed row's `Enter` commits the count it was armed with. `x` passes N to a count-taking command and repeat-calls a repeat-N one. An empty count or `0` cancels: the prompt's `Enter` closes it, issues no command, and leaves no footer note, the prompt closing being its answer as it is for `Esc` — save where the prompt's row has gone, which that `Enter` reports as any does (The count prompt); on the nap row a cancel leaves any arming as it stood. `X` runs every row it acts on one unit per call until the core refuses or the cap is reached: a repeat-N row's command as it stands, a count-taking command with a count of one on each call — one squad, one caravan at a time — and a count row's assign. Like `Enter` and `x`, `X` makes no affordability pre-check: on a Teased or unaffordable row it runs all the same, and a first call the core refuses reads as `Enter`'s refusal (A run that stops short). The cap is ten thousand calls, and it bounds the count prompt's count too (Count-prompt bound).

  *When a run's calls are made.* A run — the prompt's ×N on a repeat-N or count row, or `X` — makes every call at the press, one after another, each against the state the call before it left, and the sim does not advance between them. The rows, their markers, and the footer are re-derived after the run, so the next frame shows the whole of it. What `X` asks for is the most the stock covers now: a run spread over the ticks that follow would keep spending whatever arrived after the press, an automatic buyer the player never set going, and would still be running under whatever keys came next.

  *A held `X`.* Held, `X` runs no more than ten times a second, the pace a held `Enter` keeps, whatever the terminal's key-repeat rate; an `X` that arrives within a tenth of a second of the last run is dropped with no footer note, as a held `Enter`'s extra repeats are. Each run it does make is a whole run, as a single press's is. `X` never reaches a heavy row, so a held `X` decides nothing the player has not asked for — the most the stock covers, again as it grows — and it takes the pace, not the distinct-press rule a heavy commit takes (TUI-NAV-051).
- **`x`/`X` on a row with nothing to count** — a *single* row, or a display-only row such as a stores row, which has no command — is a no-op with a footer ("nothing to count here"). A single row has no quantity for a count or a maximum to scale, and Enter is there for its one call. `X` on a heavy row, whatever its tag and DeepNap included, is a no-op with its own footer instead — that the row takes a deliberate `Enter`, not `X` — since `X` may never be the press that commits a heavy action (TUI-NAV-051), and a note that there is nothing to count would be untrue of DeepNap. `x` on a heavy single row says there is nothing to count, as on any single row. The owned check above comes before either.
- **The count prompt.** `x` opens the prompt on every row whose command is tagged count-taking or repeat-N, and on a count row, unless the owned rule above holds the row first. DeepNap is the one heavy row among them: there the prompt's `Enter` arms rather than fires (the DeepNap sequence below); on every other the prompt's `Enter` acts. Like Enter, `x` makes no affordability pre-check: a Teased or unaffordable row opens the prompt as an affordable one does, and `Enter` attempts the count, the core arbitrating each call. The prompt belongs to the row it was opened on, held by that row's content identity — the cursor cannot move beneath it (TUI-NAV-059), and its `Enter` acts on that row or on nothing, never on whichever row the cursor would fall to without it. The sim keeps ticking beneath the open prompt, and a section's rows are re-derived from current state on every frame, so nothing guarantees the prompt's row stays listed while the prompt is open. While its row is not listed the prompt previews nothing, since there is nothing current to price; if the row is still not listed when `Enter` is pressed, the prompt closes with no effect and a footer note that the row has gone.
- **Count-prompt preview.** The prompt previews only what the core reports, never a price the shell derives from the content tables or a rule of its own. An empty or zero count previews nothing; a nonzero count previews what that count will cost, row by row:
  - *repeat-N* — the total cost of taking that count, as the core reports it from current state (SIM-ENG-038), escalation included — never summed from single-step prices, which would be the escalation rule reimplemented outside the core. The core totals content items, and every repeat-N row is one. The total prices every call in the count; where the core refuses a call partway — the stock runs short, or a one-shot has been bought — the run stops there and says so (below), and nothing past the refusal is spent. Where the core's total names no resource, because the item is priced in something outside the resource vocabulary, the prompt shows the count alone and the inspector states the price.
  - *Pounce and Trade* — N times the core's price for one unit (SIM-ENG-047), per component. That query answers only for a command priced a fixed amount per unit, and promises that N units cost exactly N times its answer, so the multiplication applies the core's own stated rule rather than one the shell holds. The previewed total is exactly what the one call passing N will spend, or ask for and be refused whole. Where the core reports no one-unit price, the prompt shows the count alone.
  - *DeepNap* — the count alone. Its price escalates with the years chosen, so the core reports no one-unit price for it, and the prompt's `Enter` does not spend: it arms the row, which states the nap's cost and wake-year from real state before a distinct `Enter` commits (TUI-NAV-036), and arming reserves nothing.
  - *a count row* — the count alone: its assign costs nothing.
- **Count-prompt bound.** The count is bounded by the same shell-side cap that bounds `X`: a digit that would carry the count past it is not taken, and it leaves a footer note that the count goes no higher — a digit is bound in the prompt, and a bound key that cannot act now says so (TUI-NAV-042) rather than reading as a lost keypress. So the prompt always shows the count `Enter` will use. The cap sits far above any count a player means; it exists so a run of mistyped digits cannot stall a frame, since both the preview and a repeat-N run walk the count one step at a time.
- **A run that stops short.** A run that repeat-calls a command — the prompt's ×N on a repeat-N or count row, or `X` on any row it runs on — reports its stop the same way. When a call is refused, the rejection surfaces as the plain-language footer (TUI-NAV-014); where at least one call went through first, the footer also states how many were done — of how many, for ×N ("3 of 10 — not enough catnip, need 12.4 more"). So a run refused on its very first call reads exactly as Enter's refusal does, and a run that did some reads as the partial success it is, with its reason for stopping. `X` always ends this way unless its cap ends it first; a run that reaches its count, or `X`'s cap, unrefused leaves no footer, the rows themselves showing what it did.
- **The DeepNap sequence is:** `x` → type years → `Enter` sets the count *and arms* the row (showing "nap N years: costs S starshards, wakes in year Y" from real state) → a second `Enter` commits. So the count prompt's Enter arms; the following Enter fires. The commit carries the count the row was armed with, since rows are rebuilt from state every frame and the typed count has nowhere else to live. An empty or zero count cancels the prompt as it does on any row, arming nothing and leaving any arming already on the row as it stood. A plain `Enter` on the unarmed row arms a nap of one year: `Enter` is a row's action ×1, and one unit of a nap is one year, as one unit of `X`'s run on a count-taking row is a count of one. Opening the prompt again on an armed nap and accepting a new nonzero count re-arms the row with that count and a fresh expiry, so the summary on screen is always the nap the next `Enter` will commit.
- **Armed rows are advisory UI only.** The second Enter re-runs the *real* command through the core, which re-validates against current state — so if the clowder dropped below 71 kittens between arming and committing the Move, the commit simply fails to the footer. Arming another heavy row (or any navigation) disarms the first.
- **The consequence summary** states only what the core reports from current state, re-derived on every frame the row is armed, so it always describes what the commit would do now. It never states a consequence the shell would have to work out by a rule of its own — a legacy gained, which kittens travel, a price assembled from the content tables — and it makes no judgement of whether the commit will be accepted: the core decides that at the commit, and a refusal is a footer (TUI-NAV-043). Row by row:
  - *the Move* — how many kittens the clowder holds, away ones included; the basket's room, as the core reports it (`basket_capacity`); and the share of stores the chest carries (`memory_chest_ratio`). What the Move earns, and which stocks it keeps whole beside the chest's share (SIM-MOVE-004), are left unstated: the core reports neither as a figure from state, and the rules behind both are the core's (Deferred).
  - *PassItDown* — the elder wisdom that passes down: the whole of the stock the core holds, which is what the command passes.
  - *an AdoptRule row* — the sibling rule it closes for this meadow. Which rule that is is a fixed fact of the rule's definition, read as its name is, not a judgement made from state. Its price is already on the row (TUI-NAV-009).
  - *DeepNap* — the armed year count, the core's cost for a nap of that length (`starshard_cost`), and the year it wakes in: the core's current year plus the count. The sum applies the core's own stated rule rather than one the shell holds: a nap the core accepts fast-forwards the meadow by exactly its count in game-years (SIM-DREAM-001). A count the core will refuse — longer than the longest nap it allows — is summarized like any other and refused at the commit; comparing the count against that limit in the shell would be the core's gate held outside it. Where a figure the core reports is not a finite number, as the cost of a count far past any real nap can be, the summary says in plain words that the cost is beyond reach rather than printing the figure.
- **An arming's life.** An arming holds until the first of these ends it: its expiry, about eight seconds of wall-clock time after it began, measured in real time because the confirm is for the player's reading, not the sim's pace; any navigation key on the screen — cursor, section, group, or digit, whether or not the key moves anything — and the palette's jump (TUI-NAV-065); `Esc` closing it (TUI-NAV-030); its commit, whether the core accepts or refuses it, so a refused commit needs a fresh arming; the arming of another row (TUI-NAV-043); or its row no longer being listed. The last is navigation by other means — the cursor has lost its row and falls back (TUI-NAV-032) — so the arming ends and the next `Enter` is an ordinary press on whatever row is focused. Nothing else ends it: toggling the inspector, opening the Journal, help, the palette, or a count prompt, retiming with the speed keys, and the sim advancing all leave the row armed beneath, its clock still running. The cursor and group keys an open Journal or help overlay takes for its own scrolling are the overlay's, their navigation meaning suspended (TUI-NAV-052), so scrolling there ends nothing; the row it covers waits, and the expiry still runs. While it holds, the row is shown expanded beneath itself in the list; while the narrow-mode swap shows the inspector in the list's place, the inspector carries the same summary. How the expanded lines are laid out and scrolled is the render leaf's: its scroll is derived from the cursor row (TUI-RENDER-009), and keeping the summary lines beneath that row on screen with it is a rule for that leaf to state (Deferred). The Resize edge case's compact re-render is the same layout concern at a smaller size. The hint bar shows the armed row's keys (`Enter yes, truly · Esc not today`) wherever no field or full-screen overlay holds the keyboard, a field's line winning over it (TUI-NAV-066). No layout ends an arming: however much of the summary a terminal has room for, full or compact, the row stays armed until one of the endings above, the hint bar's keys showing it armed whatever the layout. The moment the arming ends, for any reason, the row collapses and nothing on screen still shows it armed — an expired arming that still read "Enter yes, truly" would promise a commit the next `Enter` does not make.
- **Palette results.** The palette's universe is the section lists themselves. A result is an *item* — the thing a row is about — in a revealed section's list. Most items carry one row; some carry several adjacent rows in their section (a craft's make row and its tinkerer count row, a colony's trade and pen-pal rows), and such an item is one result; a kitten is one row, and so one result. Every item with a selectable row in a revealed section is a result — content, the fixed action rows, the stores rows, kittens, colonies, sites, and the declare-list rows alike — and nothing else is: group headers are never results, and an item with no row (Hidden content, an undiscovered colony, a gated action) is never one. So Teased items are in, because Teased rows are listed, and a kind the core reports only as present or absent (TUI-NAV-053) is in exactly when present. Drawing from the lists means every result lands somewhere and nothing the cursor can reach is missing. Each result shows its item's name beside its section's digit, and each item is its own result — two items sharing a name are never merged, so neither silently vanishes from the list. The results are re-derived from current state as the sim ticks beneath the open palette, so they always match what the sections would show now, and `Enter` takes the top result as listed at the moment of the press.
- **Palette matching and order.** The query matches as typed, spaces included, and every comparison ignores case. A result matches when its name contains the query. Matches rank by closeness — a name equal to the query, then names beginning with it, then names containing it elsewhere — with ties in tab-bar order, then list order. A query that is empty or nothing but spaces is no query: it lists every result in tab-bar then list order and aims at nothing, since a stray `Space` is not a search. The list is drawn from its top, so the result `Enter` takes is always the first one shown and always on screen, however many follow it.
- **Palette pick.** `Enter` closes the palette, moves to the top result's section, and focuses that item's first row there — it performs no row action. With no query or no match, `Enter` does nothing and the palette stays open as typed: there is no aimed result, and a jump the player did not aim is a surprise, not a shortcut; `Esc` is the way out. The jump is navigation, so it does what any other move does: it disarms an armed row, dismisses the report banner, and counts as a visit to the section it lands in. It moves the cursor, not the layout — with the narrow-mode inspector swapped in, the swap stays and shows the landed row, as it follows every other cursor move.
- **A field's accepting Enter** is spent on the field — the count prompt's ×N, the palette's jump. A held or auto-repeating continuation of that press never acts on the row the field returns to; that row acts again only on a distinct Enter, judged as a heavy row's commit is (TUI-NAV-051). The reason is the one that stops repeat at arming: key-repeat is a machine typing, not a player deciding, and without this a held Enter after a palette jump would start buying whatever it landed on.
- **Cursor landing on a section's first visit** (no identity memory yet): the first *Available* (actionable) row, else the first row. If a remembered item has since become Hidden (e.g. structures reset by a Move), the cursor falls back to the same rule.
- **The opening focus.** Every sitting — a new game or a load — opens on the Meadow, entered as a visit before the first frame of play is drawn, the cursor landing by the rule above. A load that wakes (The Waking Screen) opens when its waking ends, against the caught-up meadow; the waking screen is not a frame of play, and the opening never sees the meadow mid-replay. The shell keeps no view state across a close, so there is no remembered section to restore, and home is the one section certain to have a tab. With no item remembered yet, it lands on the gather row, on a new game and a load alike: the Meadow's first row, a fixed action row that wears `●` whenever it is listed, and always listed. The opening takes what it finds as known: no tab present at the opening wears `★`, and the `★N new` chip, which counts badged tabs, opens at nothing, so the badge and the chip mark only what appears during the sitting. On a new game that is the Meadow's one tab and its first rows; on a load it is everything the save and its catch-up hold. The opening is not a navigation key: it retires no report banner, so a load's report, queued as the game opens (TUI-NAV-027), is still the first thing the returning player sees, and the report and the Journal tell what the absence brought.
- **A focused section that empties.** When the section in focus stops listing any selectable row, it stays in focus and keeps its tab while it does; nothing moves on its own. Its list is empty, so the cursor rests on no row. Where no field or full-screen overlay holds the keyboard, `Enter`, `x`, `X`, `+`/`=`, and `-`/`Backspace` find nothing to act on and do nothing but leave one footer note, the same for each, that the section holds nothing to act on just now — each is a bound key that cannot act now, and says so rather than reading as a lost keypress (TUI-NAV-042). The cursor and group keys move nothing, as at a list's end, and are navigation all the same (TUI-NAV-083). The inspector has no row to describe. While the section holds focus its tab is in the bar, so its own digit answers as any tab's does: a visit to the section already in focus, the cursor finding nothing to land on. The player leaves as from any section — another digit, a section cycle, the palette — and once the section is out of focus with nothing listed, its tab leaves the bar and it is no longer a revealed section: a section cycle passes over it, and its digit is a no-op with a footer note, as any section's without a tab is (TUI-NAV-005), until a row returns and brings the tab back, badged. If a row returns while it is still in focus, the cursor lands as it does on entering a section (TUI-NAV-008, TUI-NAV-032). Focus never moving, everything else stands as it was: the report banner showing, any open overlay or field, and the layout. A count prompt stays held to its row (TUI-NAV-072), which belongs to the section in focus: while the row is not listed the prompt previews nothing and its `Enter` closes it with the note that the row has gone, and if the row returns first, `Enter` acts on it there. Any arming has already ended, its row having left its list (TUI-NAV-076).
- **`l`/`h`/Tab/BackTab wrap around** the revealed-section ring (last → first, first → last).
- **Tab bar overflow.** Ten revealed tabs with names do not fit 80 columns, so the tab bar is width-responsive: full `[N Name]` when it fits, else a compact digit strip (`1 2 3̶ 4 …` with the focused and `★`-badged tabs labelled) — never truncated mid-name, never scrolled off. Section names are only ever shown where they fit; the digit is the stable identity.
- **Hint-bar overflow.** When the context keys exceed the width, the shell drops the least-relevant keys first and always keeps `? keys` last; the full set is always available via `?`.
- **Narrow-mode inspector swap.** While the inspector occupies the list's space (80-col mode), the swap is a layout, not a field or a full-screen overlay: with neither of those open, every key of the global table keeps its meaning. `↑`/`↓`/`j`/`k` and the group keys `[`/`]` still move the underlying cursor and the inspector follows it, so the player can browse inspected items; the section keys, the digits, and the palette's jump (TUI-NAV-065) move focus as they always do, and the swap stays, showing the row the cursor lands on. Each of these is navigation exactly as in the list view — it ends an arming (TUI-NAV-076) and retires the showing banner (TUI-NAV-083), whether or not it moves anything. The acting keys — `Enter`, `x`, `X`, `+`/`-`, a mnemonic — act as they do in the list view and leave the swap in, and the palette, the Journal, or help opened over it take the body as they would over the list, the swap waiting beneath until they close. Only two keys return the list view, at the row the cursor is on: `Space` (or `i`) wherever the global table holds it (TUI-NAV-003), and `Esc` when the swap is the topmost transient (What `Esc` closes). Where the section in focus lists nothing, the swap stays with no row to describe, the layout standing as it does for a focused section that empties.
  - *What the list would draw on the row.* While the inspector holds the list's space, it carries what the list draws on the focused row, so nothing about that row goes unseen: an armed row's consequence summary (TUI-NAV-077), and an open count prompt's count and preview (TUI-NAV-067), shown while the inspector describes the row the prompt is held to (TUI-NAV-072). The prompt opened in the swap leaves it in, as every other acting key does; the open prompt takes `Space` as it takes any key but a digit (TUI-NAV-037), so the swap stays until the prompt closes.
- **What `Esc` closes.** Each `Esc` press closes exactly one transient, the topmost open, in this order:
  1. a field — the count prompt or the palette — or a full-screen overlay, the Journal or help; at most one of these is ever open, since each holds the keys that would open another;
  2. an armed row;
  3. the narrow-mode inspector swap;
  4. the report banner showing.

  Everything beneath the one it closes stands as it was: a field closed over an armed row leaves the row armed, its expiry still running (TUI-NAV-076); an arming ended with the swap in leaves the swap in, the inspector describing the same row without the summary; the swap returned with a banner showing leaves the banner (TUI-NAV-083). The armed row closes before the swap because, while a row is armed, the hint bar names `Esc` as the arming's own `Esc not today` (TUI-NAV-077), and the key does what the bar shows; the swap is a layout the player chose, where the arming is a question awaiting an answer. Whether the swap is in is judged by the layout on screen when `Esc` is pressed — the inspector drawn in the list's place — with the breakpoint's dead-band applied as the layout applies it (TUI-NAV-047): inside the dead-band a terminal narrower than the breakpoint can still be showing the pane, and an `Esc` spent on a swap that is not on screen would visibly do nothing. The persistent pane at a wide terminal is not a transient, and `Esc` never closes it.
  - *A bare screen.* With none of the four open, `Esc` does nothing: it closes nothing, moves nothing, and leaves no footer note. A bound key that cannot act says so elsewhere (TUI-NAV-042), but `Esc` is the one key the terminal can deliver without a fresh press — a stray or late `Esc` under `escape-time` — so a note would answer a keypress the player may never have made.
  - *What it never does.* `Esc` issues no command, moves neither the cursor nor the section, and counts as no visit — it is neither an act nor navigation. On a list that offers a choice to decline, such as the Legacy declare list's stand-down row, `Esc` does not choose it; that row is chosen with `Enter`, as any row is. `Esc` leaves no footer note in any case, the transient disappearing being its answer, and a footer note is not a transient: it answers the last press, often with why the core refused it, and leaves on its own clock, so `Esc` leaves it showing.
  - *What it discards.* What `Esc` closes is view state, and none of it is lost: the swap, an overlay, and an arming are a keypress from opening again, and a banner's report stays in the Journal (TUI-NAV-027). The one thing it discards is what an open field held — the count or query typed so far — and the next field opens empty.
  - *A held `Esc`.* A held `Esc` closes one transient for each press the terminal delivers, its repeats included: every close is harmless, so `Esc` takes none of the distinct-press rule that guards a heavy commit (TUI-NAV-051).
  - *A fused `Esc`.* Under tmux's `escape-time`, an `Esc` followed closely by another key can reach the game fused with it, as that key's Alt/Meta chord. No such chord is bound (TUI-NAV-001), so the fused pair is ignored whole: neither the `Esc`'s close nor the key's own meaning happens, and the player presses again. An `Esc` that arrives on its own, however late, is an ordinary `Esc` and leaves nothing behind for the next key to join: a key after it means what it means alone.
- **Breakpoint hysteresis:** the pane/swap inspector breakpoint (~100 cols) uses a small dead-band so a one-column resize wobble never flickers the layout.
- **What a resize keeps.** The view state is the player's and the terminal's size is not, so a resize — any change of size, one into or out of the too-small card included — changes how the view state is drawn and none of it. The section in focus and each section's remembered row stay (TUI-NAV-008), so the cursor rests on the same row, which the list's derived scroll keeps on screen at the new height (TUI-RENDER-009). An open field keeps what has been typed into it, and the count prompt the row it is held to (TUI-NAV-072); an open full-screen overlay stays open at its scroll position; an arming holds, its expiry running on (TUI-NAV-076); the banner showing stays the one showing, and no queued report is read; a footer note keeps its own clock; and the inspector call stands. A resize is neither a key nor navigation: it ends no arming, retires no banner, reads no report, counts as no visit, and badges or clears nothing. What a resize does change is derived from the size every frame — the layout and its dead-band (TUI-NAV-047), the list's scroll, the tab bar's and the header's width steps, the banner's clauses — so no stored value is left for a resize to make stale.
  - *The inspector call across the breakpoint.* The call is held at every width and changed only where the narrow layout is on screen (The inspector call), so a resize never sets or clears it, and neither does any key pressed while the pane or the card is drawn. With the swap in, a widening past the breakpoint shows the list beside the pane, and narrowing back brings the swap in again; a list view widened and narrowed again is the list view — whatever keys were pressed while the pane was drawn between.
  - *Under the too-small card.* The card is drawn in place of the whole frame, and everything beneath it stands; the sim advances while it shows (TUI-RENDER-004, TUI-RUN-017). Keys pressed while it shows keep the meanings they have at every size and act on the view state beneath, unseen; the two judged by the layout on screen, `Space` (or `i`) and `Esc`'s swap step, find no swap drawn, so the call stands, `Space` leaving no note (The inspector call), and `Esc` passes over it to the banner (What `Esc` closes). Whether the card should hold these keys instead is weighed under Decisions & Alternatives (Keys under the too-small card). Returning to 80×24 or more draws the frame the view state describes, with whatever the sim and those keys did meanwhile. What the sim does under the card ends what it ends at any size: an arming whose expiry passes or whose row leaves its list ends (TUI-NAV-076), and a cursor whose row stops being listed falls back (TUI-NAV-032). The card's words are one line, `this pane is too cozy — 80×24 needed`: it says, calmly, that nothing is wrong, and names the size the game needs, 80 columns by 24 rows, so the player knows what to widen. The card has room for that line whole wherever the pane is at least as many columns wide as the line and at least one row tall, and there it draws the line whole. How the line is fitted to a pane narrower than it is a layout rule the render leaf does not yet state (Deferred).
- **Attention-chip specifics.** Each chip is re-derived every frame from its own opportunity, and clears on its own signal and on no other chip's.
  - *`★N new`* counts the tabs in the tab bar wearing `★` (TUI-NAV-006), and nothing else. The badge already marks the one arrival the shell tracks, a tab appearing in the bar, so the chip holds no count of its own and can never disagree with the tab bar. Its count falls by one as each badged tab is visited, and also as a badged tab leaves the bar unvisited, since a badge that is no longer drawn marks nothing. The chip clears once no tab in the bar wears `★`. The opening badges no tab, so the chip opens at nothing (the opening focus). The section in focus never wears `★`: entering it is a visit, and its tab never leaves the bar while it holds focus. So the chip never counts the section the player is standing in, and every tab it counts is one the player can reach with a key. Under the compact tab bar every badged tab keeps its name (TUI-NAV-034), so each place the chip counts is named on screen.
  - *`~away`* shows while any report in the queue is unread (TUI-NAV-050), whether an absence's catch-up or an accepted nap retained it. It clears once no report stays unread, a report being read when its banner retires while showing or when the Journal opens (below). Opening the Journal therefore clears it at once, though every entry stays pinned until that Journal closes. A report left unread in an earlier sitting is not queued again, so it never lights the chip. Stacked reports, such as a load's report and then a nap taken in the same session, queue their banners newest-first, and all persist as pinned Journal entries.
  - *`!sky`* shows while the core holds a sky-event window pending and the tick has not reached the expiry the core recorded for it. SIM-ENG-025 states that a window is observable until that expiry and then simply fades, so the comparison applies the core's own stated rule; a core query answering whether a window is observable now would replace it (Deferred). The window is the one `o` observes, and it closes when the player observes it or when it fades. Its remaining time is not in the chip.
  - *One press, two signals.* A press can carry the signals of two chips at once. For example, a digit landing in a badged section while a banner shows both visits the section and retires the banner (TUI-NAV-083). Each chip answers its own signal from that press, and neither clears because the other did.
- **The report banner and its pinned entry.**
  - *Which reports get one.* A report gets a banner and a pinned entry exactly where the core retained it as a journal entry, whatever route brought it there — a load's catch-up spanning at least the core's minimum interval (SAVE-015), or an accepted nap (SIM-DREAM-008). The shell reads which reports those are from the journal, never from a minimum span of its own, which would be the core's retention rule held outside it. A load's catch-up too short for the core to keep leaves no banner, so no banner is ever shown whose dismissal would lose its report; a first run, or a load the core refuses, has no report at all. The core keeps every nap, however short, so every accepted nap queues a banner the moment it is accepted.
  - *The queue.* A report is unread from the moment it is queued until it is read. One banner shows at a time, the newest unread report's, and retiring it brings up the next newest. A report is read at the first of: its banner retired while showing, or the Journal opened — opening the Journal opens onto every entry pinned at its top, so `e` reads every unread report at once. A read report leaves the queue, so no banner shows for a report the player has already opened in the Journal. The queue is view state, not saved state: a report still unread when the game closes is not queued again on a later load, and its Journal entry, which the core keeps for good, holds it.
  - *What retires the showing banner.* `Esc`, when nothing else `Esc` closes is open above it — no field, overlay, armed row, or narrow-mode inspector swap: the banner is the last transient `Esc` closes (TUI-NAV-030), so with the swap in, one `Esc` returns the list view (TUI-NAV-017) and the next retires the banner; and any navigation key on the screen — cursor, section, group, or digit, whether or not the key moves anything — and the palette's jump (TUI-NAV-065). Each such press retires the one banner showing, never the whole queue. Acting — `Enter`, `x`, `X`, `+`/`-`, a mnemonic (TUI-NAV-081) — toggling the inspector, the speed keys, opening help, the palette, or a count prompt, the keys a full-screen overlay takes for its own scrolling (TUI-NAV-052), and the sim advancing leave it showing: none of them leaves the place the player returned to.
  - *The line.* It opens with how much time passed. For an absence, that is the span the core reports, humanized, stated as *more than* that span where the report is `truncated` — the core replays no further than its cap, so the span is a floor, not the absence. For a nap, it is the nap's length in years as the core's `Napped` event reports it, in place of a span: the report's span is attended time, which reads as hours for a nap the player chose in years. Then the largest gains — positive net changes only, largest amount first, at most three, each resource named as its stores row names it, leaving out any gain too small to show as more than zero. Then the number of kittens who arrived — the sum of the report's arrival counts — where any did. Then the hints `e for the tale` and `Esc dismiss`. Where no stock grew and no kitten arrived, a quiet note (`the meadow kept quiet`) stands in place of the gains, and the line still points at the tale, which may hold what the line leaves out. Nothing on the line reads the wanderings, the returns, the seasons passed, or a stock that fell.
  - *At narrow width.* The line fits the pane by dropping whole clauses, never by cutting one, in this order: `Esc dismiss` (`Esc` closes every transient, and navigation retires the banner too), the third gain, the second gain, `e for the tale`, the arrivals, the largest gain — or the quiet note, where it stands in the gains' place. The span is never dropped. The clauses that remain keep their order.
  - *The pinned entry.* While its report is unread, the entry sits at the top of the Journal above the scrollback, the newest first, and the Journal opens at its top, so `e` — the banner's own pointer — opens onto the tale. The opening that reads a report does not move its entry: every entry pinned when the Journal opens stays pinned, in the same order, until that Journal closes, so the tale does not leave the place the player opened onto while they read it. Once its report is read and no Journal viewing holds it, the entry keeps its place in the scrollback by when the core retained it — at once for a report read by its banner retiring, and on the Journal's closing for one read by the Journal opening. It tells the whole report: the span the core reports, humanized as an absence's line states it — more than that span where the report is `truncated`, with a gentle note that the meadow stopped counting there; every resource whose stock changed, signed, gains before decreases and each largest first; each kitten who arrived, by name; each kitten who wandered, by name, as a visit to the neighbour's yard — the one place a wandering kitten goes — that ends back home; each kitten who came home, by name, as a homecoming; and the seasons that passed. In each of the three kitten lists a name appears once, with its count where the report counts more than one.
  - *Occurrences, not whereabouts.* The report's lists count what happened, not where anyone ended up: a kitten may leave and come home several times within one span, and one away before the span began may come home and leave again (SAVE-008). So the entry never says who is away now — the roster shows that, from the core — and it never states a kitten total, a kitten count net of departures, or a wandering as anything lost.
- **DeclareAdventure(None)** is reachable as a "declare nothing / stand down" row in Legacy, chosen with `Enter` like any row (What `Esc` closes); the Family Album is a browse-only view in Legacy (no command); UnassignTinkerer is the `-` on a Tinkerer count row.

## Core API Dependencies (a small cascade into `clowder-core`)

The shell renders from existing surface except for these read-only additions, which keep rule knowledge in the core (per the engine-owns-visibility decision). They are a separate arrow segment (the sim leaves), flagged here because the navigation segment cannot fully land without them:

1. **`net_rate(ResourceId) -> f64`** — net per-second at current state (production stack minus consumption). Powers sidebar rates and the inspector's time-to-afford. This math currently lives only inside `tick()`.
2. **`lock_reason(content) -> LockReason`** (or equivalent) — the plain "why locked" per content kind. The shell *can* read `prereqs`/`gate`/`StructureGate`, but a core query keeps the rule logic core-side.
3. **Availability coverage** — an availability answer for every content kind, a kind with no reveal ladder answering present or absent and never Teased (SIM-ENG-032), beside a price's coverage as a fraction (SIM-ENG-039); the lock reason above answers ownership and whether the item can be taken now. The shell renders exactly what these report and invents no state they did not give it (TUI-NAV-053), so it needs no branch of its own for any kind.
4. **`max_affordable(...) -> u32`** (optional) — lets `X` and the hint bar name a closed-form count; without it, `X` loops-until-error under a cap.
5. **The per-unit price of a count-taking command** — the price of one unit, per component, of a command that takes its count as an argument and is priced a fixed amount per unit (a Pounce's squad, a Trade's caravan to the colony it names), answering nothing for a command priced otherwise (a nap's price escalates with its length), for one that takes no count, and for one the command layer would refuse as locked (SIM-ENG-047). Powers the inspector's next cost on Pounce and Trade rows and the count prompt's preview there — N times the one-unit price, by the query's own promise that N units cost that — so the shell never assembles a price from the content tables.

A blank breaks the glyph column; `○` calls every such row unaffordable, a claim as unfounded as any and one that steers the player away from actions that work; the craft's lock reason speaks of making it, not of binding a tinkerer; a coverage worked out in the shell is affordability judged outside the core. A refused `Enter` names any shortfall in the footer, and a core report for these rows would let them wear `◐` and `○` (Deferred) |
| Full resource table | Rows in Meadow's "stores" group (inspectable) | A dedicated resources tab | Saves a digit; sidebar stays display-only |
| Groups within a section | One group per kind of row; every group of a section with several kinds headed, the first included, while it lists a row; a section with one kind unheaded | Headers only while two or more groups are listed; a header on every section, the single-kind one included; headers over runs of rows wherever they happen to stand, leaving a kind split | A header that waits for a second group would insert a line above rows the player already sees, moving the cursor's row down the pane as content arrives; on a single-kind section a header only repeats the tab's name; a kind split under two headers of the same words reads as two kinds |
| Space between groups | The header line alone | A blank line above each header | A blank line costs a body row per group at the 20-row floor, and the dim rule already marks the break |
| What a kitten's row says it is doing | One state per kitten in its count and cost fields' place: `visiting` for a kitten away, whatever its job; else its job's name as the job's row spells it; else `idle` | The job's name for a kitten away, with a mark that it is away; `away` for a kitten away; a glyph for each state; nothing, the job's count rows alone saying who works where | A kitten away keeps its job but works none of it, and its job's count row leaves it out, so naming the job would read as work being done and disagree with the count above it. `away` is the word of the header chip that says an unread report waits, and one word meaning two things in one frame reads as either. A glyph beside the marker reads as a marker, and a code to learn is the opposite of a word read at a glance. The count rows say how many kittens hold a job but not which, so a player looking for whom to move has to guess |
| Group header words | Plain plural nouns for the kind; `things to do` for every section's fixed actions | Flavor words per section; the section's own name; a verb per section | A header is structure, not content: the flavor lives on the rows it heads (tenet 3), and one recurring phrase lets a kind read the same wherever it appears |
| Glyph set | Single-width geometric/box chars only; no emoji | Emoji flourish | wcwidth ambiguity breaks columns across terminals/tmux |

## Open Questions & Future Decisions

### Resolved
1. ✅ **Journal retention.** The journal is saved state, so it survives closing the game — which is what makes a report the player never got to read safe. It keeps a bounded rolling window of recent events plus every milestone and report permanently; the core owns the ring and the eviction rule (SIM-ENG-027, SIM-ENG-029). Unbounded retention was the alternative, and it turns every autosave of a months-long game into a growing rewrite.

### Deferred
1. Exact widths/breakpoints — refined in the `render` leaf against a real terminal.
2. A core report of how many more copies an item can take would let the count prompt price a one-shot buy at one copy rather than at the count as typed. The core offers no such report, and the shell may not derive it (Decisions & Alternatives: preview of a buy the core will stop at one).
3. A core report of the largest count a count-taking command's stock covers would let `X` make one call passing it — one journal entry for the run rather than one per unit. The core offers no such report, and the shell may not derive it (Decisions & Alternatives: `X` on a count-taking row).
4. A core report of what a Move would earn from current state, and of which stocks it keeps whole beside the chest's share, would let the Move's armed summary state both beside what comes along. The core offers no such report, and the shell may not derive it (Decisions & Alternatives: consequence summary's content).
5. The render leaf's scroll keeps the cursor row in view (TUI-RENDER-009); an armed row's summary expands in lines beneath that row, and keeping those lines in view with it, full or compact, is a rule for the render leaf to state. Until it does, an armed row near the viewport's bottom can have summary lines below the visible range; the hint bar's armed keys, and the inspector's copy of the summary where it is shown, keep the arming visible meanwhile.
6. A core report of whether an action with no content item, or a craft's tinkerer bind, can be taken now, and of how far current stock covers its price, would let those rows wear `◐` and `○` rather than `●` alone. The core offers no such report, and the shell may not derive it (Decisions & Alternatives: marker on a row the core reports no lock reason for).
7. The core's coverage fraction reads only prices in the resource vocabulary, so it reports an item priced in something outside it as covered whole. While such an item stands short, its lock reason names the shortfall and its row wears `◐` however little of the price is held, never `●`. A coverage answer that reads such a price would let the row wear `○` when none is held; until the core gives one, the row wears what the core reports.
8. The core's cost query names no price outside the resource vocabulary, so the inspector states no next cost for an item priced there, and its shortfall reason names no amount. A core report of such a price would let the inspector state it with need and have. The shell may not read it from the content tables (What the inspector states).
9. The core's prerequisite reason does not say which prerequisite is unmet, so the inspector cannot name it. A core report naming it would let the reason point at what to do next; the shell may not work it out from the gates (Core API Dependencies).
10. Fixed actions have no content definitions, and some kinds' definitions carry nothing that says what the item does, so their rows have no mechanical statement. Definitions in the core's tables that describe them would let the inspector state one (Decisions & Alternatives: mechanical statement's scope).
11. A core report of a job's yield per worker after mood, and of what an item's owned copies contribute at current state, would let the inspector state both beside the definition's own terms. The core offers neither, and the shell may not derive them (Decisions & Alternatives: mechanical statement's scope).
12. The core's retained report does not say whether a nap or an absence folded it, so a nap's pinned entry states its span in attended time, not in the years chosen, while its banner names the years from the nap event. A core marking of a retained report's route, carrying a nap's length, would let the entry name the nap as its banner does; the shell may not work years out from the span (Decisions & Alternatives: how much time a nap's banner says passed).
13. The core reports a pending sky-event window by the expiry it recorded, and no query answers whether that window is observable now, so the `!sky` chip compares the tick against that expiry, applying SIM-ENG-025's stated rule. A core query answering by the gate `ObserveSky` meets would let the chip read the core's answer instead (Resolved Edge Cases: attention-chip specifics).
14. Keys pressed under the too-small card act on a screen the player cannot see (Resolved Edge Cases: What a resize keeps). The sharpest case is an arming carried into the card: a second `Enter` there commits a heavy action with its consequence summary out of sight, where the distinct second press (TUI-NAV-051) and the summary it confirms (TUI-NAV-075) exist to make that press one the player has just read. A navigation key or a banner's retiring under the card likewise changes what the player returns to without showing it. Cozy and whimsy-with-clarity both weigh toward the card holding the keys — all but quitting, the speed keys, and `Esc` — as a full-screen overlay holds its own, and idle-respect is untouched either way, since the sim advances under the card regardless. Holding would change what the key specs let those keys do at a size they cover, so it is a change to the keys themselves, weighed under Decisions & Alternatives (Keys under the too-small card).
15. The too-small card's line needs as many columns as it is wide, and a pane can be narrower. How the line is fitted to such a pane — cut, wrapped, or shortened to the figures alone — is a layout rule for the render leaf to state. TUI-NAV-087 holds wherever the card has room for the line whole, as Resolved Edge Cases (What a resize keeps: under the too-small card) defines that room.
16. A later row's label (Action Model: an item's rows) reads as belonging to the row above it. How the list sets it to read that way — where in the name's column it begins — and how it is fitted where that column is too narrow for it are layout rules for the render leaf to state beside TUI-RENDER-020 and TUI-RENDER-014. A label the list cuts short is read whole in the inspector, beneath the item's name (What the inspector states). Until that leaf states them, a label stands where a name would and is fitted as a name is. The hint a kitten's row carries after its name (Per-screen mnemonics: the row-bound key) sits in the same column, and where in it the hint begins after the name is likewise a layout rule for the render leaf to state. What gives way when the column is short is not layout but which of the row's words must stand, and this leaf fixes it: the hint is drawn whole or not at all, and never at the cost of a character of the name. Until that leaf states the hint's place, the hint follows the name after one blank column. The Elder's mark (The Action Model: who the Elder is) stands in that same place on the Elder's row, and where in the column it begins is the same layout rule; which of that row's words gives way is again this leaf's: the mark gives way to the name, its word before its glyph. Until the render leaf states the place, the mark follows the name after one blank column, as the hint does, and that blank column is part of the room the mark needs.
17. The render leaf lays out the game's frame (TUI-RENDER-002) and gives way to the too-small card below the floor (TUI-RENDER-004); the waking screen stands in the frame's place as that card does (The Waking Screen). Where its three lines sit and how the bar is fitted to a pane narrower than its line are layout rules for the render leaf to state beside TUI-RENDER-004. Until that leaf states them, the lines are centred in the pane, one blank row between each.
18. The core classes the event of an appointment as a milestone (engine leaf: Event Vocabulary), and its journal keeps every milestone permanently (SIM-ENG-027, SIM-ENG-029). An appointment is free and repeatable, and the core answers one for the kitten who is already the Elder as it answers any other, its event included, so nothing bounds how many a playthrough makes: every press of `n` the core accepts adds a permanent Journal entry — up to ten a second while the key is held (TUI-NAV-094), and on the Elder's own row for an appointment that changed nothing (Decisions & Alternatives: `n` on the Elder's own row). The engine leaf keeps the milestone class for occurrences bounded over a playthrough by construction (SIM-ENG-042), which an appointment is not. Which class an appointment's event takes, and whether an appointment that changes nothing emits one, are the engine leaf's rules; settling them is a change to that segment, across this leaf's boundary, so it waits on that leaf and is not made from here. This leaf does not bound the entries from the shell meanwhile: issuing the command less often than the key is pressed, or not at all on the Elder's row, would be a rule about appointments held outside the core, and would not bound them either, since alternating `n` between two kittens' rows writes as many.
19. The Elder's mark takes only the room a kitten's name leaves in its column (The Action Model: who the Elder is), so a row whose name fills that column, or leaves less than the glyph's place, carries no mark, and the roster does not say there who the Elder is. No other cell of a kitten's row is free for it: past the cursor and the marker the row is its name's column, one blank column, and the fields' place that carries the kitten's state, blank after its word, and the width and place of each is the render leaf's (TUI-RENDER-020, TUI-RENDER-024). Room the name cannot take from the mark — a place for the glyph outside the name's column, or a floor on the name's column in the Clowder list — is therefore a column rule for the render leaf to state; it is a change to that segment, across this leaf's boundary, and is not made from here. Until that leaf states one, such a row carries no mark and the inspector's line says the kitten is the Elder (What the inspector states: the Elder).
